Setup, Configuration & Logging SQL

Before you optimize anything you need to see the SQL EF Core runs. This lesson covers registering a DbContext properly, the options worth knowing, and making EF show you what it's doing.

⏱ 25 min
🎯 Goal of this lesson

Get a correctly configured DbContext running quickly and, above all, make EF show you the SQL it executes. That habit underpins the rest of the course.

Why it matters: Most EF performance problems are invisible until you look at the generated SQL. Logging and the right lifetime from day one prevent whole classes of bugs. Level 2 then goes deeper into configuration.

By the end of this lesson you will be able to

  • Register a DbContext in ASP.NET Core with the right lifetime.
  • Configure provider options: connection strings, timeouts, retries.
  • Log generated SQL with LogTo and ILoggerFactory, and filter the output.
  • Know which diagnostic options are safe in production and which are not.

Registering the DbContext

In ASP.NET Core, register the context with dependency injection. AddDbContext registers it with a scoped lifetime: one instance per HTTP request. That's exactly the unit-of-work lifetime you want.

var builder = WebApplication.CreateBuilder(args);

builder.Services.AddDbContext<ShopContext>(options =>
    options.UseSqlServer(
        builder.Configuration.GetConnectionString("Shop"),
        sql =>
        {
            sql.CommandTimeout(30);                 // seconds
            sql.EnableRetryOnFailure(               // transient fault handling (Lesson 17)
                maxRetryCount: 5,
                maxRetryDelay: TimeSpan.FromSeconds(10),
                errorNumbersToAdd: null);
        }));
{
  "ConnectionStrings": {
    "Shop": "Server=.;Database=Shop;Trusted_Connection=True;TrustServerCertificate=True;Max Pool Size=200"
  }
}
Lifetimes matter
  • Never register a DbContext as a singleton. It isn't thread-safe and its change tracker grows forever.
  • Don't inject a scoped DbContext into a singleton service such as a hosted BackgroundService. Inject IDbContextFactory<T> or IServiceScopeFactory and create a short-lived context per unit of work.

When you need a factory

Blazor Server, background workers and parallel processing need several short-lived contexts inside one scope. Register a factory:

builder.Services.AddDbContextFactory<ShopContext>(o => o.UseSqlServer(connStr));

public class NightlyReportJob(IDbContextFactory<ShopContext> factory) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken ct)
    {
        await using var db = await factory.CreateDbContextAsync(ct);
        var count = await db.Orders.CountAsync(o => o.Status == OrderStatus.Pending, ct);
        // ...
    }
}

Seeing the SQL

This is the most important habit in the whole course: always know what SQL your code produces. There are several ways to see it.

1. LogTo: quick and simple

options.UseSqlServer(connStr)
       .LogTo(Console.WriteLine, LogLevel.Information);

Filter the output to just executed commands:

options.LogTo(
    Console.WriteLine,
    new[] { DbLoggerCategory.Database.Command.Name },
    LogLevel.Information);

2. ASP.NET Core logging: the production-friendly way

AddDbContext automatically picks up the application's ILoggerFactory. Control verbosity in appsettings.Development.json:

{
  "Logging": {
    "LogLevel": {
      "Default": "Information",
      "Microsoft.EntityFrameworkCore.Database.Command": "Information"
    }
  }
}

Every executed command is then logged with its duration:

info: Microsoft.EntityFrameworkCore.Database.Command[20101]
      Executed DbCommand (4ms) [Parameters=[@customerId='42'], CommandType='Text', CommandTimeout='30']
      SELECT [o].[Id], [o].[CustomerId], ... FROM [Orders] AS [o] WHERE [o].[CustomerId] = @customerId

3. ToQueryString(): inspect without executing

var query = db.Orders.Where(o => o.Total > 100).OrderBy(o => o.PlacedUtc);
Console.WriteLine(query.ToQueryString());   // great in unit tests and in the debugger

Diagnostic options

OptionWhat it doesProduction?
EnableSensitiveDataLogging()Includes parameter values and entity key values in logs and exception messages. (EF 10 also redacts constants it inlines into SQL unless this is on.)❌ No. It leaks PII and secrets.
EnableDetailedErrors()Better errors when materialization fails (e.g. a null in a non-nullable column). Small overhead.⚠ Development only
LogTo(...)Simple logging to a delegate.⚠ Prefer ILogger
ConfigureWarnings(...)Turns specific EF warnings into errors, or ignores them.✅ Yes
 
builder.Services.AddDbContext<ShopContext>(options =>
{
    options.UseSqlServer(connStr);

    if (builder.Environment.IsDevelopment())
    {
        options.EnableSensitiveDataLogging()
               .EnableDetailedErrors();
    }

    // Fail fast on patterns that hurt performance (see Lessons 12 and 15)
    options.ConfigureWarnings(w => w
        .Throw(RelationalEventId.MultipleCollectionIncludeWarning));
});
Turn performance warnings into errors in development EF logs warnings for risky patterns. Examples: loading several collections in one query (cartesian explosion), and First() without OrderBy (CoreEventId.FirstWithoutOrderByAndFilterWarning). Throwing on these in development catches problems before they reach production.

Connection pooling: already on

ADO.NET providers pool physical database connections by default. Opening and closing a SqlConnection just borrows from and returns to the pool. EF opens the connection as late as possible and closes it as early as possible, which is the right behaviour. Tune pool size in the connection string (Max Pool Size, default 100 for SqlClient) only if you see pool exhaustion errors under load.

Connection pooling ≠ DbContext pooling Connection pooling (ADO.NET) reuses database connections. DbContext pooling (EF, Lesson 20) reuses DbContext objects. They solve different problems and work together.

🔑 Key takeaways

  • Register the context with AddDbContext (scoped). Use a factory for singletons and background work.
  • Always know your SQL: LogTo, ILogger categories, and ToQueryString().
  • EnableSensitiveDataLogging and EnableDetailedErrors are for development only.
  • Turn EF performance warnings into exceptions during development.

Exercise

🛠 Make EF talk

  1. Add LogTo filtered to DbLoggerCategory.Database.Command in your playground.
  2. Run db.Customers.FirstAsync(). What warning appears, and what SQL is generated?
  3. Print db.Orders.Where(o => o.Total > 500).ToQueryString(). Notice the literal 500: constants in the expression become SQL literals, while variables become parameters.
  4. Enable EnableSensitiveDataLogging and compare the logged parameters.
What you should see

FirstAsync() without ordering gives a warning that results may be unpredictable, because the database doesn't guarantee row order without an ORDER BY. The SQL is SELECT TOP(1) ... FROM [Customers]. With sensitive logging on, parameters show their real values (@id='42'). Otherwise they appear as '?'.

Quiz

What lifetime does AddDbContext use by default?

Scoped means one instance per request, which matches the unit-of-work pattern.

Which option should never be on in production?

It writes parameter values (emails, tokens, personal data) into logs.

A BackgroundService needs database access. What's the best approach?

Hosted services are singletons. A factory gives you correctly scoped, short-lived contexts.
