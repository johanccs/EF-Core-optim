Modeling Fundamentals

Many performance problems start in the model. Unbounded string columns, wrong decimal types and missing relationships turn into slow queries later. This lesson shows how to configure a model deliberately.

⏱ 30 min

By the end of this lesson you will be able to

  • Explain EF Core's conventions and how to override them.
  • Choose between data annotations and the Fluent API, and organize configuration with IEntityTypeConfiguration<T>.
  • Configure keys, relationships, column types, lengths and precision.
  • Apply model-wide defaults with ConfigureConventions.

Conventions: what you get for free

EF Core builds the model by convention. A few defaults matter for performance:

ConventionDefaultPerformance consequence
Property named Id or <Type>IdPrimary key. Integers use IDENTITY on SQL Server.Fine. Lesson 11 covers HiLo and sequences for batching.
string propertiesnvarchar(max) on SQL Server⚠ Can't be used as an index key. Larger memory grants. Worse plans.
decimal propertiesdecimal(18,2), with a warning⚠ May silently truncate values. Configure precision explicitly.
Foreign key propertiesAn index is created automatically✅ Joins and FK lookups are indexed.
EnumsStored as int✅ Compact. Strings are more readable but larger.
Nullable reference types enabledstring → NOT NULL, string? → NULL✅ Accurate nullability lets EF generate simpler SQL.

Data annotations vs Fluent API

Data annotations 
public class Product
{
    public int Id { get; set; }

    [Required, MaxLength(32)]
    public string Sku { get; set; } = "";

    [Precision(10, 2)]
    public decimal Price { get; set; }
}
Fluent API 
modelBuilder.Entity<Product>(b =>
{
    b.Property(p => p.Sku)
     .IsRequired()
     .HasMaxLength(32);

    b.Property(p => p.Price)
     .HasPrecision(10, 2);
});

The Fluent API is more powerful: indexes, filters, table splitting, conversions and query filters are Fluent-only. It also keeps persistence concerns out of your domain classes. A common team convention is Fluent API only, one configuration class per entity:

public class ProductConfiguration : IEntityTypeConfiguration<Product>
{
    public void Configure(EntityTypeBuilder<Product> b)
    {
        b.ToTable("Products");
        b.HasKey(p => p.Id);

        b.Property(p => p.Sku).HasMaxLength(32).IsUnicode(false);   // varchar(32)
        b.Property(p => p.Name).HasMaxLength(200);                   // nvarchar(200)
        b.Property(p => p.Description).HasMaxLength(4000);
        b.Property(p => p.Price).HasPrecision(10, 2);

        b.HasIndex(p => p.Sku).IsUnique();

        b.HasOne(p => p.Category)
         .WithMany(c => c.Products)
         .HasForeignKey(p => p.CategoryId)
         .OnDelete(DeleteBehavior.Restrict);
    }
}

Column types and why they matter

Strings: always set a max length

nvarchar(max) columns are stored differently. SQL Server can't use them as index key columns, and the optimizer has to assume large values when sizing memory grants. Use HasMaxLength for anything with a natural limit. Use IsUnicode(false) (varchar) for ASCII-only data such as SKUs, codes and hashes. It halves storage.

Parameter type mismatch: a classic index killer If a column is varchar but the parameter is sent as nvarchar, SQL Server must convert the column side and may stop using its index. EF sizes and types parameters from the model, so configure IsUnicode(false) in the model. Don't leave the database and the model out of sync.

Model-wide defaults with ConfigureConventions

Instead of repeating configuration per property, set defaults once. This is pre-convention model configuration:

protected override void ConfigureConventions(ModelConfigurationBuilder configurationBuilder)
{
    configurationBuilder.Properties<string>().HaveMaxLength(256);
    configurationBuilder.Properties<decimal>().HavePrecision(18, 2);
    configurationBuilder.Properties<DateTime>().HaveColumnType("datetime2(3)");
    configurationBuilder.Properties<OrderStatus>().HaveConversion<string>().HaveMaxLength(16);
}

Individual entity configuration still wins, so Description can override the 256 default with HasMaxLength(4000).

Relationships

Define relationships explicitly when conventions are ambiguous, and choose delete behaviour on purpose:

modelBuilder.Entity<Order>(b =>
{
    b.HasOne(o => o.Customer)
     .WithMany(c => c.Orders)
     .HasForeignKey(o => o.CustomerId)
     .OnDelete(DeleteBehavior.Restrict);      // don't cascade-delete order history

    b.HasMany(o => o.Lines)
     .WithOne()
     .HasForeignKey(l => l.OrderId)
     .OnDelete(DeleteBehavior.Cascade);       // lines belong to the order
});
Expose foreign key properties Having CustomerId as a real property, not just the Customer navigation, lets you filter and set relationships without loading the related entity: order.CustomerId = 42 instead of order.Customer = await db.Customers.FindAsync(42). That saves a whole query.

Keys

  • int / bigint identity: compact, sequential, fast to index. The default choice.
  • GUID: globally unique and generated client-side, but random GUIDs fragment clustered indexes. If you use GUIDs, prefer sequential ones. EF's SQL Server provider generates sequential GUIDs client-side by default for key properties. In .NET 9+, Guid.CreateVersion7() gives time-ordered GUIDs.
  • Natural keys (e.g. Sku): usually better as a unique index than as the primary key, because they can change and are wider.

Quiz

What does an unconfigured string property map to on SQL Server?

Unbounded nvarchar(max) can't be an index key column, so configure max lengths. (Key columns default to nvarchar(450).)

Does EF Core create indexes for foreign keys by convention?

EF creates FK indexes by convention. Other indexes, like those for WHERE and ORDER BY columns, are up to you (Lesson 9).

Where do you configure model-wide defaults such as "all strings are max 256"?

Pre-convention configuration in ConfigureConventions applies before conventions run, and per-property config can still override it.
