Querying Fundamentals

Knowing where a query runs is the foundation of EF Core performance: in the database, or in your application's memory. This lesson covers deferred execution, IQueryable versus IEnumerable, client evaluation and async.

⏱ 30 min
🎯 Goal of this lesson

Understand where and when a query runs: in the database or in memory, now or later, and choose LINQ operators that keep the work on the database server.

Why it matters: One misplaced ToList() or IEnumerable can turn a 1-row query into a full table download. This is the most common and most expensive beginner mistake.

By the end of this lesson you will be able to

  • Tell when a query executes, and avoid executing it twice.
  • Keep filtering, sorting and aggregation in the database.
  • Recognize accidental client-side evaluation.
  • Use async queries, streaming and the right terminal operators.

Deferred execution

An IQueryable<T> is a description of a query. Each operator (Where, OrderBy, Select) adds to the expression tree. Nothing runs until a terminal operation enumerates it:

  • Materializers: ToList, ToArray, ToDictionary (and their async versions)
  • Single-result operators: First, Single, Any, Count, Sum, Max…
  • foreach / await foreach
IQueryable<Order> query = db.Orders.Where(o => o.Status == OrderStatus.Paid);

if (minTotal is not null)
    query = query.Where(o => o.Total >= minTotal);      // composable: still no SQL

if (sortByDate)
    query = query.OrderByDescending(o => o.PlacedUtc);

var page = await query.Take(50).ToListAsync();          // ONE SQL query here
Enumerating twice runs the query twice 
var paid = db.Orders.Where(o => o.Status == OrderStatus.Paid);
var count = paid.Count();          // query 1: SELECT COUNT(*)
foreach (var o in paid) { }        // query 2: SELECT ...
var list = paid.ToList();          // query 3: SELECT ...
Materialize once with ToList() if you need the data several times. If you only need a count, ask the database for the count and nothing else.

IQueryable vs IEnumerable

This is the most expensive beginner mistake. Once a query becomes an IEnumerable<T>, every later operator runs in memory, on all the rows already fetched.

❌ Filters in memory 
IEnumerable<Order> GetOrders() => db.Orders;

var big = GetOrders()
    .Where(o => o.Total > 1000)   // LINQ-to-Objects!
    .ToList();
// SQL: SELECT * FROM Orders  (all rows!)
✅ Filters in SQL 
IQueryable<Order> GetOrders() => db.Orders;

var big = await GetOrders()
    .Where(o => o.Total > 1000)
    .ToListAsync();
// SQL: ... WHERE [o].[Total] > 1000.0

The same thing happens with AsEnumerable(), with a ToList() too early in the chain, and with repository methods that return IEnumerable<T> or List<T> when callers still need to filter.

Client evaluation

EF Core 3.0 and later throw an exception if a Where or OrderBy contains something that can't be translated to SQL. That's good: it stops accidental full-table downloads.

// Throws InvalidOperationException: "The LINQ expression ... could not be translated"
var vip = db.Customers.Where(c => IsVip(c)).ToList();

static bool IsVip(Customer c) => c.Email.EndsWith("@bigcorp.com");

Fix it by writing the logic as a translatable expression:

var vip = await db.Customers.Where(c => c.Email.EndsWith("@bigcorp.com")).ToListAsync();

There is one exception: client evaluation is allowed in the final Select, because it only runs on rows already fetched:

var dtos = await db.Customers
    .Select(c => new { c.Id, Display = FormatName(c.Name) })   // FormatName runs in .NET: OK
    .ToListAsync();
Explicit client evaluation If you really must evaluate something in memory, make it obvious: filter as much as possible in SQL, then call AsEnumerable() or ToListAsync(), then apply the client-side logic.

Picking the right operator

Does any row exist?AnyAsync(predicate) → EXISTSCountAsync() > 0, or ToList().Any()
Exactly one row by unique keySingleOrDefaultAsync (fetches TOP 2 to verify) or FirstOrDefaultAsync (TOP 1)Where(...).ToList().FirstOrDefault()

Async: scalability, not speed

Async queries (ToListAsync, FirstOrDefaultAsync, SaveChangesAsync) don't make a single query faster. They free the thread while waiting on I/O, so a web server can handle more concurrent requests with fewer threads. Use async in web apps and services, and pass the CancellationToken through so abandoned requests stop their queries.

app.MapGet("/customers/{id:int}/orders", async (int id, ShopContext db, CancellationToken ct) =>
    await db.Orders.Where(o => o.CustomerId == id).ToListAsync(ct));
Known SqlClient caveat With Microsoft.Data.SqlClient, reading very large text or binary columns (several MB of nvarchar(max) or varbinary(max)) asynchronously has been much slower than reading them synchronously. If you hit this, project those columns away, or read them separately in sync code.

Buffering vs streaming

ToListAsync() buffers: all rows are loaded into memory before you see the first one. To process a large result set row by row with constant memory, stream it:

await foreach (var order in db.Orders.AsNoTracking().Where(o => o.Status == OrderStatus.Paid).AsAsyncEnumerable())
{
    await exporter.WriteAsync(order);     // one row in memory at a time
}

Streaming keeps the connection open for the whole loop. Keep the loop body fast, and don't run other queries on the same context inside it unless MARS is enabled. Streaming with tracking still accumulates entities in the change tracker, so use AsNoTracking() (Lesson 10).

Exercise

🛠 Spot the hidden queries

How many SQL queries does this code run, and how much data does it fetch? Rewrite it.

public List<Customer> GetCustomers() => db.Customers.ToList();

var customers = GetCustomers();
var withEmail = customers.Where(c => c.Email.Contains("@shop.test")).ToList();
var hasAny = withEmail.Count() > 0;
var total = db.Orders.ToList().Where(o => o.Status == OrderStatus.Paid).Sum(o => o.Total);
Show solution

The original runs 2 queries, but it downloads every customer and every order. Rewritten:

IQueryable<Customer> Customers() => db.Customers;

var hasAny = await Customers().AnyAsync(c => c.Email.Contains("@shop.test"));     // EXISTS(...)
var total  = await db.Orders.Where(o => o.Status == OrderStatus.Paid)
                            .SumAsync(o => o.Total);                              // SELECT SUM(...)

Two queries that each return one value, instead of two full table scans pulled into memory.

Quiz

A method returns IEnumerable<Order> from db.Orders. The caller adds .Where(o => o.Total > 100). Where does the filter run?

IEnumerable switches to LINQ-to-Objects, so every row is fetched first.

Where is client-side evaluation allowed in EF Core 3+?

Only the final projection can run arbitrary .NET code. Untranslatable filters throw.

What's the main benefit of ToListAsync() over ToList() in a web API?

Async improves throughput under concurrency, not single-query latency.
