DbContext Configuration in Depth

Lesson 2 got you running. This lesson explains how a DbContext actually receives its configuration, so you can set it up correctly in web apps, background workers, the dotnet ef tools and tests.

⏱ 35 min
🎯 Goal of this lesson

Understand every path by which configuration reaches a DbContext: dependency injection, OnConfiguring, factories, strongly-typed options and design-time factories. Then choose the right one for each kind of application.

Why it matters: most "it works on my machine" EF problems are configuration problems. Typical examples are a context created without a provider, settings applied in two places that override each other, migrations that can't find the context, and lifetimes that leak state. Once you can see the whole configuration pipeline, these become easy to diagnose.

By the end of this lesson you will be able to

  • Explain how DbContextOptions<T> is built and in what order configuration runs.
  • Pick between AddDbContext, OnConfiguring, AddDbContextFactory and manual construction.
  • Bind database settings from appsettings.json with validated, strongly-typed options.
  • Configure several DbContexts in one application, each with its own migrations.
  • Make the dotnet ef tools work with IDesignTimeDbContextFactory<T>.

The configuration pipeline

A DbContext is configured through a DbContextOptionsBuilder. The finished, immutable DbContextOptions<TContext> holds the provider (SQL Server, PostgreSQL…), the connection, logging, interceptors and behaviour switches. Configuration can come from two places:

  1. Outside the context: the delegate passed to AddDbContext, or a DbContextOptionsBuilder you build yourself and pass to the constructor.
  2. Inside the context: the OnConfiguring override, which runs after the external options are applied, every time a context instance is initialized.
public class ShopContext : DbContext
{
    public ShopContext(DbContextOptions<ShopContext> options) : base(options) { }

    protected override void OnConfiguring(DbContextOptionsBuilder optionsBuilder)
    {
        // Only fall back to a local database if nobody configured us from outside
        if (!optionsBuilder.IsConfigured)
        {
            optionsBuilder.UseSqlite("Data Source=shop-dev.db");
        }
    }
}
Two sources, one winner If both AddDbContext and OnConfiguring set the same option, OnConfiguring runs last and wins. Guard any fallback configuration in OnConfiguring with IsConfigured, or, better, don't use OnConfiguring at all in applications that use DI.

Resolving services while configuring

The overload of AddDbContext that takes the IServiceProvider lets you pull interceptors, configuration or environment information from DI:

builder.Services.AddSingleton<SlowQueryInterceptor>();

builder.Services.AddDbContext<ShopContext>((sp, options) =>
{
    var db = sp.GetRequiredService<IOptions<DatabaseOptions>>().Value;
    options.UseSqlServer(db.ConnectionString, sql => sql.CommandTimeout(db.CommandTimeoutSeconds))
           .AddInterceptors(sp.GetRequiredService<SlowQueryInterceptor>());
});

Strongly-typed, validated settings

Scattering Configuration["..."] lookups and magic numbers through Program.cs makes configuration hard to review and easy to break. Bind a settings class once, validate it, and fail at startup instead of at the first query:

{
  "Database": {
    "ConnectionString": "Server=.;Database=Shop;Trusted_Connection=True;TrustServerCertificate=True",
    "CommandTimeoutSeconds": 30,
    "MaxRetryCount": 5,
    "EnableSensitiveDataLogging": false
  }
}
public sealed class DatabaseOptions
{
    public const string Section = "Database";

    [Required] public string ConnectionString { get; init; } = "";
    [Range(1, 600)] public int CommandTimeoutSeconds { get; init; } = 30;
    [Range(0, 10)] public int MaxRetryCount { get; init; } = 5;
    public bool EnableSensitiveDataLogging { get; init; }
}
builder.Services.AddOptions<DatabaseOptions>()
    .Bind(builder.Configuration.GetSection(DatabaseOptions.Section))
    .ValidateDataAnnotations()
    .ValidateOnStart();                              // app refuses to start with bad settings

builder.Services.AddDbContext<ShopContext>((sp, options) =>
{
    var db = sp.GetRequiredService<IOptions<DatabaseOptions>>().Value;
    options.UseSqlServer(db.ConnectionString, sql =>
    {
        sql.CommandTimeout(db.CommandTimeoutSeconds);
        if (db.MaxRetryCount > 0) sql.EnableRetryOnFailure(db.MaxRetryCount);
    });
    if (db.EnableSensitiveDataLogging) options.EnableSensitiveDataLogging();
});
Keep secrets out of appsettings.json The example above shows the shape of the settings. The real connection string, especially one containing a password, belongs in user-secrets, environment variables or a vault. Lesson 6 covers this.

Multiple DbContexts

Large applications often split the model into several contexts, for example one per bounded context (Sales, Catalog, Identity). Smaller contexts build faster and keep teams independent. Each context can have its own schema and migrations history:

builder.Services.AddDbContext<SalesContext>(o => o.UseSqlServer(connStr,
    sql => sql.MigrationsHistoryTable("__EFMigrationsHistory", "sales")));

builder.Services.AddDbContext<CatalogContext>(o => o.UseSqlServer(connStr,
    sql => sql.MigrationsHistoryTable("__EFMigrationsHistory", "catalog")));

public class SalesContext(DbContextOptions<SalesContext> options) : DbContext(options)
{
    protected override void OnModelCreating(ModelBuilder b) => b.HasDefaultSchema("sales");
}
dotnet ef migrations add InitialSales   --context SalesContext   --output-dir Migrations/Sales
dotnet ef migrations add InitialCatalog --context CatalogContext --output-dir Migrations/Catalog
Use the generic options type With more than one context, each constructor must take DbContextOptions<TContext> for its own type, not the non-generic DbContextOptions. Otherwise DI can hand one context the other context's options.

Design-time configuration (dotnet ef)

Commands like dotnet ef migrations add need to create your context without running your app normally. The tools try, in order:

  1. An IDesignTimeDbContextFactory<TContext> implementation in the project.
  2. The application's host: they call your Program and read the context from its service provider.
  3. A parameterless constructor on the context.

When startup does things the tools can't handle (it needs secrets, connects to other services, or lives in another project), add a design-time factory:

public class ShopContextDesignTimeFactory : IDesignTimeDbContextFactory<ShopContext>
{
    public ShopContext CreateDbContext(string[] args)
    {
        var options = new DbContextOptionsBuilder<ShopContext>()
            .UseSqlServer(Environment.GetEnvironmentVariable("SHOP_DESIGNTIME_CONNECTION")
                          ?? "Server=.;Database=Shop;Trusted_Connection=True;TrustServerCertificate=True",
                          sql => sql.MigrationsAssembly("Shop.Migrations"))
            .Options;
        return new ShopContext(options);
    }
}

MigrationsAssembly tells EF to store migrations in a separate project. That's useful for keeping migrations out of the domain assembly, or for maintaining separate migration sets per provider.

Exercise

🛠 Production-grade configuration

  1. Create DatabaseOptions, bind it with ValidateOnStart, and configure ShopContext from it.
  2. Delete the CommandTimeoutSeconds value, set it to 0, and start the app. Confirm it refuses to start, with a clear message.
  3. Split out a small CatalogContext (Products, Categories) with its own schema and history table, and create a migration for each context.
  4. Add a design-time factory and run dotnet ef dbcontext info --context ShopContext.
What you should see

With an invalid value the host throws OptionsValidationException at startup, naming the failing property. That's much better than a timeout exception at 3 a.m. dotnet ef dbcontext info prints the provider, database name and options in use. It's a quick way to confirm which configuration the tools picked up.

Quiz

Both AddDbContext and OnConfiguring set a command timeout. Which value is used?

OnConfiguring runs last. Guard fallbacks with optionsBuilder.IsConfigured.

What does ValidateOnStart() give you for database settings?

Fail fast: configuration errors surface during deployment, not under user traffic.

When do the dotnet ef tools use an IDesignTimeDbContextFactory<T>?

The factory is checked first, which makes design-time creation independent of your app's startup code.
