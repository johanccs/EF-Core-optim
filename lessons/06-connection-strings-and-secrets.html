Connection Strings, Secrets & Connection Pooling

The connection string is the most important line of EF configuration. It decides security, resiliency, pooling behaviour and even how your app shows up in database monitoring. This lesson covers how to write, store and tune it.

⏱ 35 min
🎯 Goal of this lesson

Learn to write connection strings on purpose: know what each important keyword does, keep credentials out of source control (ideally with no password at all), and understand ADO.NET connection pooling well enough to configure and troubleshoot it.

Why it matters: a leaked connection string is a security incident. A wrong timeout or pool setting causes outages under load. A missing Application Name makes production problems much harder to trace. All of these are fixed in configuration, not code.

By the end of this lesson you will be able to

  • Read and write SQL Server and PostgreSQL connection strings, keyword by keyword.
  • Build connection strings safely in code with connection string builders.
  • Store secrets with user-secrets, environment variables and Azure Key Vault, and go passwordless with managed identity.
  • Explain how connection pooling works, and diagnose pool exhaustion.

Anatomy of a SQL Server connection string

Server=tcp:shop-sql.database.windows.net,1433;Database=Shop;
Authentication=Active Directory Default;Encrypt=True;
Application Name=Shop.Api;Connect Timeout=30;Max Pool Size=200;
KeywordDefaultWhat it does / guidance
Server / Data Source(required)Host, instance and port. tcp: forces TCP.
Database / Initial CatalogLogin's default DBAlways set it explicitly.
AuthenticationSQL / WindowsActive Directory Default, Active Directory Managed Identity and others enable passwordless Entra ID auth.
EncryptTrue (Microsoft.Data.SqlClient 4+)Keep it on. Local dev against a self-signed certificate needs TrustServerCertificate=True. Never use that in production.
Application NameA generic SqlClient nameShows in sys.dm_exec_sessions, Query Store and Extended Events. Set it for every app.
Connect Timeout15 sTime allowed to open a connection. This isn't the query timeout, which is EF's CommandTimeout.
Max Pool Size / Min Pool Size100 / 0Pool limits per unique connection string. See below.
MultipleActiveResultSetsFalseMARS allows several open readers on one connection. It adds overhead, so enable it only if you need it.
ApplicationIntent=ReadOnlyReadWriteRoutes to readable secondaries (Always On, Azure SQL read scale-out). Use it for a read-only context.
MultiSubnetFailoverFalseFaster failover for availability-group listeners across subnets.
ConnectRetryCount / ConnectRetryInterval1 / 10 sIdle connection resiliency: transparently reconnects broken idle connections. It complements EF's EnableRetryOnFailure.

PostgreSQL (Npgsql) equivalents

Host=shop-pg.postgres.database.azure.com;Port=5432;Database=shop;Username=shop_api;
SSL Mode=Require;Application Name=Shop.Api;Maximum Pool Size=100;Timeout=15;Command Timeout=30

Npgsql recommends configuring connections through an NpgsqlDataSource and passing that to EF. It's the central place for pooling, authentication callbacks, logging and type mappings:

var dataSource = new NpgsqlDataSourceBuilder(builder.Configuration.GetConnectionString("Shop")).Build();
builder.Services.AddDbContext<ShopContext>(o => o.UseNpgsql(dataSource));

Building connection strings safely

Never concatenate connection strings from user input. Use the provider's builder, which escapes values and validates keywords:

var csb = new SqlConnectionStringBuilder(builder.Configuration.GetConnectionString("Shop"))
{
    ApplicationName = "Shop.Api",
    MaxPoolSize = 200,
    Encrypt = SqlConnectionEncryptOption.Mandatory
};
options.UseSqlServer(csb.ConnectionString);

Storing secrets

Never commit credentials Passwords in appsettings.json end up in git history, container images and CI logs forever. Assume anything committed is public.

Development: user-secrets

dotnet user-secrets init
dotnet user-secrets set "ConnectionStrings:Shop" "Server=.;Database=Shop;User Id=dev;Password=…;TrustServerCertificate=True"

Secrets live in your user profile, outside the repository, and are loaded automatically in the Development environment.

Servers and containers: environment variables

The .NET configuration system maps __ (double underscore) to :, so the variable below overrides ConnectionStrings:Shop:

export ConnectionStrings__Shop="Server=…;Database=Shop;…"

Cloud: a secret store

// Azure Key Vault configuration provider (Azure.Extensions.AspNetCore.Configuration.Secrets)
builder.Configuration.AddAzureKeyVault(
    new Uri("https://shop-kv.vault.azure.net/"),
    new DefaultAzureCredential());
// a secret named "ConnectionStrings--Shop" becomes ConnectionStrings:Shop

AWS Secrets Manager, HashiCorp Vault and Kubernetes secrets have equivalent configuration providers or mounting options.

Best: no password at all

With managed identities (Azure) or IAM authentication (AWS RDS), the app authenticates with its platform identity. There's no secret to leak or rotate:

Server=tcp:shop-sql.database.windows.net;Database=Shop;Authentication=Active Directory Default;Encrypt=True

Active Directory Default uses DefaultAzureCredential: your developer login locally, the managed identity in Azure. For Azure Database for PostgreSQL, Npgsql's data source builder can fetch short-lived Entra tokens as passwords through a periodic password provider.

Connection pooling explained

Opening a physical connection involves TCP, TLS and authentication handshakes, which take milliseconds or more. ADO.NET providers therefore keep a pool of open connections:

  • Open() borrows an idle connection from the pool, or creates one if the pool is below Max Pool Size.
  • Close() or Dispose() returns it to the pool after resetting session state.
  • There is one pool per distinct connection string (and, for integrated auth, per identity).
  • When the pool is full, Open() waits up to Connect Timeout, then throws.

EF opens a connection just before each command and closes it right after (unless you hold a transaction or open it explicitly), so connections spend very little time out of the pool.

Pool fragmentation Building a different connection string per tenant or per user creates a separate pool for each. Hundreds of small pools waste connections and defeat pooling. Prefer one connection string plus tenant filtering (Lesson 24), or a bounded set of tenant databases.

Diagnosing pool exhaustion

System.InvalidOperationException: Timeout expired. The timeout period elapsed prior to obtaining
a connection from the pool. This may have occurred because all pooled connections were in use
and max pool size was reached.

Raising Max Pool Size is rarely the fix. Look for what is holding connections:

  • Long transactions, or long-running streaming queries (Lessons 4 and 17).
  • Contexts or connections that aren't disposed (a missing using, a long-lived context).
  • Sync-over-async (.Result, .Wait()) causing thread-pool starvation. Requests pile up while holding connections.
  • Slow queries. Each request holds its connection longer, so concurrency needs more connections (Little's law: connections ≈ requests per second × seconds per query).

🔑 Key takeaways

  • Know the important connection string keywords: Encrypt, Application Name, timeouts, pool sizes, ApplicationIntent.
  • Secrets never go in source control. Use user-secrets in dev, environment variables or a vault in prod, and managed identity where possible.
  • There is one connection pool per distinct connection string. Per-tenant strings fragment pools.
  • Pool exhaustion is almost always connections held too long, not a pool that's too small.

Exercise

🛠 Secure and observable connections

  1. Move your playground connection string to dotnet user-secrets and delete it from appsettings.json.
  2. Add Application Name=EfPlayground, run a query, and find your session with SELECT session_id, program_name FROM sys.dm_exec_sessions WHERE program_name = 'EfPlayground'.
  3. Set Max Pool Size=5 and fire 50 concurrent requests that each run WAITFOR DELAY '00:00:02' through ExecuteSqlAsync. Observe the pool timeout, then explain it with Little's law.
Explanation

Five connections, each busy for 2 seconds, give a maximum of about 2.5 queries per second. 50 concurrent requests have to queue. Those waiting longer than Connect Timeout fail. The fix is shorter queries, not a bigger pool.

Quiz

What does Connect Timeout in a SQL Server connection string control?

Query duration is EF's CommandTimeout. Connect Timeout covers opening and acquiring a connection.

Why is a different connection string per tenant a performance problem?

Pools are keyed by connection string. Many small pools mean many more open connections.

Which option avoids storing a database password anywhere?

Environment variables and vaults still hold a secret. Managed identity removes it entirely.
