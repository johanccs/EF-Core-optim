Model Configuration at Scale

Configuring five entities is easy. Configuring two hundred consistently is a design problem. This lesson covers organizing model configuration so it stays correct, reviewable and uniform as the model grows.

⏱ 35 min
🎯 Goal of this lesson

Learn to structure model configuration for a real, growing codebase: where each kind of configuration belongs, how precedence works, how to apply rules model-wide, and how to seed and inspect the model with confidence.

Why it matters: inconsistent configuration causes subtle bugs and slow queries: some strings bounded and others not, some decimals truncated, enums stored differently in different tables. Centralized rules and a clear structure make the correct choice the default, and make deviations obvious in code review.

By the end of this lesson you will be able to

  • Explain configuration precedence: conventions, data annotations, Fluent API.
  • Organize configuration with IEntityTypeConfiguration<T> and shared base configurations.
  • Apply model-wide rules with ConfigureConventions, including global value converters.
  • Configure schemas, naming, default values and computed columns.
  • Choose between HasData and UseSeeding for seed data.

Precedence: who wins?

EF builds the model in layers. Later, more explicit layers override earlier ones:

  1. Pre-convention configuration (ConfigureConventions): defaults for types, applied before conventions run.
  2. Conventions: EF's built-in rules (keys named Id, FK discovery…) plus any custom conventions.
  3. Data annotations: [MaxLength], [Required], [Precision], etc.
  4. Fluent API in OnModelCreating: always wins.
Pick one primary style Mixing annotations and Fluent API for the same concern makes it hard to know what's actually configured. Common team rule: use the Fluent API for everything persistence-related, and keep entities free of EF attributes.

Shared column rules belong in an abstract base configuration:

public interface IAuditable { DateTime CreatedUtc { get; set; } DateTime? ModifiedUtc { get; set; } }

public abstract class AuditableConfiguration<T> : IEntityTypeConfiguration<T> where T : class, IAuditable
{
    public virtual void Configure(EntityTypeBuilder<T> b)
    {
        b.Property(e => e.CreatedUtc).HasDefaultValueSql("SYSUTCDATETIME()");
        b.Property(e => e.ModifiedUtc);
    }
}

public sealed class OrderConfiguration : AuditableConfiguration<Order>
{
    public override void Configure(EntityTypeBuilder<Order> b)
    {
        base.Configure(b);
        b.ToTable("Orders", "sales");
        b.Property(o => o.Total).HasPrecision(12, 2);
        b.HasIndex(o => new { o.CustomerId, o.PlacedUtc });
    }
}

// ShopContext.OnModelCreating
modelBuilder.ApplyConfigurationsFromAssembly(typeof(ShopContext).Assembly);

Model-wide rules with ConfigureConventions

protected override void ConfigureConventions(ModelConfigurationBuilder c)
{
    // Type defaults
    c.Properties<string>().HaveMaxLength(256);
    c.Properties<decimal>().HavePrecision(18, 2);
    c.Properties<DateTime>().HaveColumnType("datetime2(3)");

    // Enums stored as readable strings everywhere
    c.Properties<Enum>().HaveConversion<string>().HaveMaxLength(32);

    // Strongly-typed IDs: one converter for the whole model
    c.Properties<CustomerId>().HaveConversion<CustomerIdConverter>();

    // Never map these types
    c.IgnoreAny<IDomainEvent>();
}

public readonly record struct CustomerId(int Value);
public sealed class CustomerIdConverter() : ValueConverter<CustomerId, int>(id => id.Value, v => new CustomerId(v));

Per-property Fluent configuration still overrides these defaults, so Product.Description can use HasMaxLength(4000) while every other string defaults to 256.

Schemas, naming and database-generated values

modelBuilder.HasDefaultSchema("shop");                                  // all tables → shop.*

modelBuilder.Entity<Order>(b =>
{
    b.ToTable("Orders", "sales", t => t.HasCheckConstraint("CK_Orders_Total", "[Total] >= 0"));
    b.Property(o => o.PlacedUtc).HasDefaultValueSql("SYSUTCDATETIME()");
    b.Property(o => o.Status).HasDefaultValue(OrderStatus.Pending);
});

modelBuilder.Entity<OrderLine>()
    .Property<decimal>("LineTotal")                                     // shadow property
    .HasComputedColumnSql("[Quantity] * [UnitPrice]", stored: true);    // persisted computed column
Defaults and the CLR default value When a property has a database default, EF only omits it from the INSERT if the property still holds its CLR default (0, null, the first enum member…). If that CLR default is also a valid value you want to save, configure a different sentinel with HasSentinel (EF 8+), or make the property nullable.

Seed data: HasData vs UseSeeding

AspectHasData (model-managed)UseSeeding / UseAsyncSeeding (EF 9+)
How it worksSeed rows become part of the model. Migrations generate INSERT, UPDATE and DELETE statements to keep them in sync.Your code runs during Migrate(), EnsureCreated() and dotnet ef database update.
KeysMust be specified explicitlyAny logic you like
Best forSmall, static reference data: countries, statuses, categoriesLarger or computed data, data depending on other data, dev and test data
 
// Static reference data
modelBuilder.Entity<Category>().HasData(
    new Category { Id = 1, Name = "Books" },
    new Category { Id = 2, Name = "Games" });

// Runtime seeding (EF 9+). Implement both for tools and app code.
options.UseSqlServer(connStr)
    .UseSeeding((ctx, _) =>
    {
        if (!ctx.Set<Product>().Any())
        {
            ctx.Set<Product>().Add(new Product { Sku = "DEMO-1", Name = "Demo", Price = 9.99m, CategoryId = 1 });
            ctx.SaveChanges();
        }
    })
    .UseAsyncSeeding(async (ctx, _, ct) =>
    {
        if (!await ctx.Set<Product>().AnyAsync(ct))
        {
            ctx.Set<Product>().Add(new Product { Sku = "DEMO-1", Name = "Demo", Price = 9.99m, CategoryId = 1 });
            await ctx.SaveChangesAsync(ct);
        }
    });

Inspecting the result

  • db.Model.ToDebugString() prints every entity, property, column type, key, index and relationship EF ended up with.
  • dotnet ef dbcontext info shows the provider, database and context options.
  • Review every migration diff. It's the clearest record of what a configuration change does to the database.

🔑 Key takeaways

  • Precedence: pre-convention configuration < conventions < data annotations < Fluent API.
  • Organize with IEntityTypeConfiguration<T> and shared base configurations. Apply model-wide rules in ConfigureConventions.
  • Use HasData for small static reference data, and UseSeeding/UseAsyncSeeding (EF 9+) for everything else.
  • Review every migration diff. It shows exactly what a configuration change does.

Quiz

A property has [MaxLength(50)] and HasMaxLength(100) in OnModelCreating. Which applies?

Fluent API configuration has the highest precedence.

When is HasData the right choice for seeding?

HasData is part of the model and migrations. Use UseSeeding (EF 9+) for dynamic or larger data.

Where do you register a value converter that should apply to every property of a type across the model?

Pre-convention configuration applies type-wide defaults in one place.
