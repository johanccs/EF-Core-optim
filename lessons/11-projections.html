Projections: Fetch Only What You Need

Projecting with Select is often the single biggest read optimization in EF Core. It shrinks the SQL result, skips tracking, lets the database use covering indexes and avoids loading graphs.

⏱ 25 min
🎯 Goal of this lesson

Master projections: shaping queries so the database returns exactly the columns your code needs, and nothing more.

Why it matters: Fetching less data is often the single biggest read optimization. It reduces I/O, network traffic, memory and tracking, and it enables covering indexes.

By the end of this lesson you will be able to

  • Project entities into DTOs, records and anonymous types.
  • Pull related data through navigation properties inside a projection, without Include.
  • Write reusable projection expressions.
  • Avoid the classic projection pitfalls.

The problem: over-fetching

A product list page needs id, name and price. Loading full entities fetches every column, including the 2 KB Description:

❌ Full entities 
var products = await db.Products
    .Where(p => p.CategoryId == 3)
    .ToListAsync();
SELECT [p].[Id], [p].[CategoryId],
  [p].[Description], [p].[Name],
  [p].[Price], [p].[Sku]
FROM [Products] AS [p]
WHERE [p].[CategoryId] = 3
✅ Projection 
var products = await db.Products
    .Where(p => p.CategoryId == 3)
    .Select(p => new { p.Id, p.Name, p.Price })
    .ToListAsync();
SELECT [p].[Id], [p].[Name], [p].[Price]
FROM [Products] AS [p]
WHERE [p].[CategoryId] = 3

Benefits of the projection:

  • Less I/O and network traffic: only three columns travel.
  • No change tracking: DTOs aren't entities.
  • Covering indexes: an index on CategoryId that INCLUDEs Name, Price can answer the query without touching the table (Lesson 14).
  • Shape matches the API: you stop leaking entities, and accidental lazy loads, into serialization.

Navigation properties inside projections

Inside a Select you can walk navigation properties freely. EF translates them into JOINs or subqueries. No Include is needed, and Include is ignored when the final result isn't an entity.

public record OrderSummary(int Id, DateTime PlacedUtc, string CustomerName, int LineCount, decimal Total);

var summaries = await db.Orders
    .Where(o => o.Status == OrderStatus.Paid)
    .OrderByDescending(o => o.PlacedUtc)
    .Select(o => new OrderSummary(
        o.Id,
        o.PlacedUtc,
        o.Customer.Name,          // JOIN Customers
        o.Lines.Count,            // correlated COUNT subquery
        o.Lines.Sum(l => l.Quantity * l.UnitPrice)))
    .Take(50)
    .ToListAsync();
SELECT TOP(@p) [o].[Id], [o].[PlacedUtc], [c].[Name],
    (SELECT COUNT(*) FROM [OrderLines] AS [o0] WHERE [o].[Id] = [o0].[OrderId]),
    (SELECT COALESCE(SUM(CAST([o1].[Quantity] AS decimal(18,2)) * [o1].[UnitPrice]), 0.0)
       FROM [OrderLines] AS [o1] WHERE [o].[Id] = [o1].[OrderId])
FROM [Orders] AS [o]
INNER JOIN [Customers] AS [c] ON [o].[CustomerId] = [c].[Id]
WHERE [o].[Status] = 1
ORDER BY [o].[PlacedUtc] DESC

Nested collections

Projections can include child collections. EF fetches them with a JOIN, or with split queries if you ask (Lesson 15):

var detail = await db.Orders
    .Where(o => o.Id == id)
    .Select(o => new
    {
        o.Id,
        Customer = o.Customer.Name,
        Lines = o.Lines.Select(l => new { l.Product.Name, l.Quantity, l.UnitPrice }).ToList()
    })
    .SingleOrDefaultAsync();

Reusable projections

Duplicating projection code everywhere is error-prone. Store it as an Expression<Func<T, TDto>>, which stays translatable to SQL:

public record ProductListItem(int Id, string Name, decimal Price, string Category)
{
    public static readonly Expression<Func<Product, ProductListItem>> Projection =
        p => new ProductListItem(p.Id, p.Name, p.Price, p.Category.Name);
}

var items = await db.Products.Where(p => p.Price < 50)
                             .Select(ProductListItem.Projection)
                             .ToListAsync();
Don't hide projections in methods or constructors EF can't see inside a C# method call or constructor body. If you write .Select(p => ToDto(p)), or a DTO constructor that takes the whole entity, then EF must fetch the entire entity and run your method client-side. The projection gives you no data reduction. Keep projections as expression trees that list exactly the columns you need.
❌ Fetches every column 
.Select(p => new ProductDto(p))   // ctor reads p.*
.Select(p => Map(p))              // opaque method
✅ Fetches 3 columns 
.Select(p => new ProductDto
{
    Id = p.Id, Name = p.Name, Price = p.Price
})

What about AutoMapper and Mapster?

Mapping libraries can generate expression-based projections: AutoMapper's ProjectTo<T>(), Mapster's ProjectToType<T>(), and source generators such as Mapperly's queryable projections. These are fine. Avoid Map<T>() on already-loaded entities, because that is the over-fetching pattern again. Always check the generated SQL.

Projection pitfalls

  • Projecting an entity inside an anonymous type (new { Product = p }) fetches every column of that entity and tracks it.
  • Nullable navigations: o.Customer.Name becomes a LEFT JOIN if the relationship is optional, so it can be null. Model the DTO property as nullable.
  • Aggregates on empty sets: Sum of an empty collection becomes 0 (EF uses COALESCE). Max or Average on empty sets need a cast to a nullable type: o.Lines.Max(l => (decimal?)l.UnitPrice).

🔑 Key takeaways

  • Project with Select to fetch only the columns the caller needs. This is often the biggest single read win.
  • Navigations inside projections become JOINs or subqueries automatically. Include isn't needed there.
  • Keep projections as expression trees. Opaque constructors and methods force full-entity fetches.
  • Projections enable covering indexes and remove tracking overhead.

Exercise

🛠 Build a lean customer dashboard query

Write one query that returns, for the 20 newest customers: Id, Name, number of orders, date of last order (nullable), and lifetime spend. Then print the SQL with ToQueryString().

Show solution 
var dashboard = await db.Customers
    .OrderByDescending(c => c.CreatedUtc)
    .Select(c => new
    {
        c.Id,
        c.Name,
        OrderCount = c.Orders.Count(),
        LastOrderUtc = c.Orders.Max(o => (DateTime?)o.PlacedUtc),
        LifetimeSpend = c.Orders.Sum(o => o.Total)
    })
    .Take(20)
    .ToListAsync();

That's one round trip with no tracking and no order rows loaded into memory. The database does all the aggregation.

Quiz

Is Include() needed to read o.Customer.Name inside a Select projection?

Include only matters when you return entities. In projections, EF joins whatever you reference.

Why is .Select(p => new ProductDto(p)) a performance trap?

EF only translates what it can see in the expression tree. Opaque constructors and methods force full-entity fetches.

Are DTO projections tracked by the change tracker?

Only entity instances are tracked. A DTO containing an entity instance still tracks that entity.
