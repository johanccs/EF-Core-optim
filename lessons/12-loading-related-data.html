Loading Related Data & the N+1 Problem

How you load related entities decides whether a page sends 1 query or 1,001. This lesson covers EF Core's three loading strategies and how to find and fix the N+1 problem.

⏱ 35 min
🎯 Goal of this lesson

Learn the three ways to load related data, and how to recognize and eliminate the N+1 query problem.

Why it matters: N+1 is the most common cause of slow pages in ORM-based apps. A page that sends 1,000 queries instead of 1 is slow no matter how fast each query is.

By the end of this lesson you will be able to

  • Use eager (Include/ThenInclude), explicit and lazy loading correctly.
  • Recognize and fix N+1 query patterns.
  • Use filtered includes to limit loaded children.
  • Decide when lazy loading is acceptable, which is rarely.

The N+1 problem

N+1 means one query to fetch a list, plus one extra query per item to fetch related data. With 100 orders, that's 101 round trips. Even at 1 ms each, the latency adds up, and on a cloud database with 2–5 ms latency the page takes half a second just waiting on the network.

❌ N+1 (explicit form) 
var orders = await db.Orders
    .Where(o => o.Status == OrderStatus.Paid)
    .ToListAsync();                         // 1 query

foreach (var o in orders)
{
    var customer = await db.Customers
        .FindAsync(o.CustomerId);           // N queries
    Console.WriteLine(customer!.Name);
}
✅ One query 
var rows = await db.Orders
    .Where(o => o.Status == OrderStatus.Paid)
    .Select(o => new { o.Id, o.Customer.Name })
    .ToListAsync();                         // 1 query (JOIN)

foreach (var r in rows)
    Console.WriteLine(r.Name);

Strategy 1: Eager loading with Include

Use eager loading when you need entities, typically to modify them, together with their related data.

var order = await db.Orders
    .Include(o => o.Customer)
    .Include(o => o.Lines)
        .ThenInclude(l => l.Product)
    .SingleAsync(o => o.Id == id);
SELECT [o].*, [c].*, [s].*
FROM (SELECT TOP(2) ... FROM [Orders] WHERE [Id] = @id) AS [o]
INNER JOIN [Customers] AS [c] ON [o].[CustomerId] = [c].[Id]
LEFT JOIN (
    SELECT [o0].*, [p].* FROM [OrderLines] AS [o0]
    INNER JOIN [Products] AS [p] ON [o0].[ProductId] = [p].[Id]
) AS [s] ON [o].[Id] = [s].[OrderId]
ORDER BY [o].[Id], [c].[Id], [s].[Id]

Filtered include

Load only the children you need. Where, OrderBy, Skip and Take are supported inside Include:

var customers = await db.Customers
    .Include(c => c.Orders
        .Where(o => o.Status != OrderStatus.Cancelled)
        .OrderByDescending(o => o.PlacedUtc)
        .Take(5))
    .ToListAsync();
Filtered include + tracking With tracking, if some of a customer's other orders were already tracked by the context, they'll still appear in customer.Orders through navigation fix-up, even though they don't match the filter. Use AsNoTracking(), or a fresh context, when the filtered collection must be exact.

Don't over-include

Every Include fetches all columns of the related table. Including collections multiplies rows (cartesian explosion, Lesson 15). For read-only screens, a projection (Lesson 11) is almost always better than a chain of Include calls.

Strategy 2: Explicit loading

Load a navigation later, on demand, for an already-tracked entity:

var customer = await db.Customers.SingleAsync(c => c.Id == id);

if (needOrders)
{
    await db.Entry(customer)
        .Collection(c => c.Orders)
        .Query()                                  // optional: compose further
        .Where(o => o.PlacedUtc > DateTime.UtcNow.AddMonths(-3))
        .LoadAsync();
}

// Count without loading the collection
var orderCount = await db.Entry(customer).Collection(c => c.Orders).Query().CountAsync();

Explicit loading is fine for a single entity. Doing it inside a loop is N+1 again.

Strategy 3: Lazy loading

With lazy loading, a navigation property loads itself from the database the first time you access it. It needs the Microsoft.EntityFrameworkCore.Proxies package, UseLazyLoadingProxies(), and virtual navigation properties.

// 1. Configuration (Program.cs)
options.UseSqlServer(connStr).UseLazyLoadingProxies();

// 2. Entities: navigation properties must be virtual (Order.cs)
//    public virtual Customer Customer { get; set; } = null!;
//    public virtual List<OrderLine> Lines { get; set; } = new();

// 3. Usage: looks innocent...
decimal total = 0;
foreach (var order in await db.Orders.ToListAsync())
    total += order.Lines.Sum(l => l.UnitPrice);   // ⚠ a hidden query per order = N+1
Why most teams disable lazy loading
  • It hides database calls behind property access, so N+1 creeps in silently.
  • JSON serializers walk every navigation, which can trigger dozens of queries or circular references.
  • Lazy loads are synchronous I/O: there's no await, so a thread blocks.
  • Accessing a navigation after the context is disposed throws.
If you do use it, turn on detection: EF logs CoreEventId.LazyLoadOnDisposedContextWarning, and you can throw on CoreEventId.NavigationLazyLoading in tests to find lazy loads.

Detecting N+1

  • Logs: repeated identical SQL with only the parameter changing is the giveaway.
  • Count commands per request: a DbCommandInterceptor (Lesson 24) can count queries and warn above a threshold.
  • APM / OpenTelemetry traces: a request span with dozens of child DB spans (Lesson 19).
  • Integration tests: assert the number of commands executed by an endpoint.

🔑 Key takeaways

  • N+1 means one query per item. It's the most common ORM performance bug.
  • Use projections for reads, Include (optionally filtered) to load graphs you'll modify, and explicit loading for single entities.
  • Lazy loading hides queries behind property access. Avoid it, or detect it in tests.
  • Detect N+1 with logs, traces, or a command-counting test.

Exercise

🛠 Kill the N+1

This code builds an "invoice" view. Count the queries, then rewrite it as one query.

var orders = await db.Orders.Where(o => o.CustomerId == customerId).ToListAsync();
var result = new List<InvoiceDto>();
foreach (var o in orders)
{
    var lines = await db.OrderLines.Where(l => l.OrderId == o.Id).ToListAsync();
    var items = new List<string>();
    foreach (var l in lines)
    {
        var p = await db.Products.FindAsync(l.ProductId);
        items.Add($"{l.Quantity} x {p!.Name}");
    }
    result.Add(new InvoiceDto(o.Id, o.PlacedUtc, items));
}
Show solution

The original runs 1 + N + N×M queries. FindAsync can skip some if products are already tracked. For 10 orders with 3 lines each, that's up to 41 queries. Rewritten:

var result = await db.Orders
    .Where(o => o.CustomerId == customerId)
    .Select(o => new InvoiceDto(
        o.Id,
        o.PlacedUtc,
        o.Lines.Select(l => l.Quantity + " x " + l.Product.Name).ToList()))
    .ToListAsync();

It's one query, and the string concatenation is translated to SQL as well.

Quiz

A page lists 200 orders and shows each customer's name using lazy loading. How many queries run, worst case?

1 query for the orders, plus 1 per distinct customer not already tracked. Worst case that's 200 more.

What happens to Include() when the query ends with a projection to a DTO?

Include only affects queries that return entity types.

Which of these is supported inside a filtered Include?

Filtered include (EF Core 5+) supports Where, OrderBy/ThenBy (and descending), Skip and Take.
