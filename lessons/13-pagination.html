Pagination: Offset vs Keyset

Returning unbounded result sets is one of the most common production incidents. This lesson covers how to page correctly, and why the obvious Skip/Take approach slows down as users page deeper.

⏱ 25 min
🎯 Goal of this lesson

Learn to return large result sets in pages correctly, and understand why keyset paging stays fast where offset paging slows down.

Why it matters: Unbounded queries cause outages as data grows, and deep offset paging degrades linearly. Correct paging keeps list endpoints fast at any size.

By the end of this lesson you will be able to

  • Always limit result sets, and know why.
  • Implement offset pagination correctly and understand its costs.
  • Implement keyset (seek) pagination, including with composite sort keys.
  • Handle total counts efficiently.

Rule #1: never return unbounded results

db.Orders.ToListAsync() is fine with 50 rows in development and an outage with 5 million rows in production. Every list endpoint should have a maximum page size enforced on the server:

const int MaxPageSize = 100;
pageSize = Math.Clamp(pageSize, 1, MaxPageSize);

Offset pagination (Skip/Take)

var skip = (pageNumber - 1) * pageSize;
var page = await db.Orders
    .AsNoTracking()
    .OrderByDescending(o => o.PlacedUtc).ThenByDescending(o => o.Id)   // deterministic order!
    .Skip(skip)
    .Take(pageSize)
    .Select(o => new { o.Id, o.PlacedUtc, o.Total })
    .ToListAsync();
SELECT [o].[Id], [o].[PlacedUtc], [o].[Total]
FROM [Orders] AS [o]
ORDER BY [o].[PlacedUtc] DESC, [o].[Id] DESC
OFFSET @skip ROWS FETCH NEXT @pageSize ROWS ONLY
Always order by a unique key Without a total ordering the database may return rows in any order, so rows can repeat or vanish between pages. Add the primary key as a tie-breaker: .ThenBy(o => o.Id).

Why offset gets slow

To return page 5,000 with 20 rows per page, the database must read and discard 99,980 rows first. Cost grows linearly with the offset. Offset paging also suffers from drift: if a row is inserted or deleted while the user pages, items shift and the user sees duplicates or misses rows.

Keyset (seek) pagination

Instead of "skip N rows", say "give me rows after the last one I saw". With an index on the sort key, the database seeks directly to the position. Page 5,000 costs the same as page 1.

// First page: lastId = null
IQueryable<Order> query = db.Orders.AsNoTracking();

if (lastId is not null)
    query = query.Where(o => o.Id > lastId);          // seek predicate

var page = await query.OrderBy(o => o.Id).Take(pageSize).ToListAsync();
var nextCursor = page.LastOrDefault()?.Id;           // return to client
SELECT TOP(@pageSize) ... FROM [Orders] AS [o]
WHERE [o].[Id] > @lastId
ORDER BY [o].[Id]

Composite sort keys

Real lists sort by something non-unique, such as date. Use (date, id) as the cursor:

public record OrderCursor(DateTime PlacedUtc, int Id);

IQueryable<Order> q = db.Orders.AsNoTracking();

if (cursor is not null)
{
    q = q.Where(o => o.PlacedUtc < cursor.PlacedUtc
                 || (o.PlacedUtc == cursor.PlacedUtc && o.Id < cursor.Id));
}

var page = await q
    .OrderByDescending(o => o.PlacedUtc).ThenByDescending(o => o.Id)
    .Take(pageSize + 1)                      // fetch one extra to know if there's a next page
    .Select(o => new { o.Id, o.PlacedUtc, o.Total })
    .ToListAsync();

var hasMore = page.Count > pageSize;
var items = page.Take(pageSize).ToList();
var next = hasMore ? new OrderCursor(items[^1].PlacedUtc, items[^1].Id) : null;

Support it with a matching composite index (Lesson 14):

modelBuilder.Entity<Order>()
    .HasIndex(o => new { o.PlacedUtc, o.Id })
    .IsDescending(true, true);                       // EF Core 7+
Encode the cursor Return the cursor to clients as an opaque string, for example Base64 of the JSON {"PlacedUtc":"…","Id":123}. Clients can't tamper with its meaning, and you can change the format later.

Total counts

"Page 3 of 1,284" needs a COUNT(*), which scans the whole filtered set on every request. Options:

  • Skip it. Show "next" and "previous" only, using the Take(pageSize + 1) trick.
  • Count only on the first page request and cache it.
  • Show an approximate count for huge tables.
var filtered = db.Orders.Where(o => o.Status == status);
var total = await filtered.CountAsync();           // round trip 1
var items = await filtered.OrderBy(o => o.Id).Skip(skip).Take(take).ToListAsync();  // round trip 2

  2. Time offset pagination for pages 1, 1,000 and 40,000 (page size 25).

  4. In SQL Server Management Studio or Azure Data Studio, look at the actual execution plans. Compare "rows read" in each.
What to expect

Offset page 40,000 reads about 1M rows. Keyset reads about 25 using an index seek. Times typically differ by one or two orders of magnitude.

Quiz

Why does Skip(100000).Take(20) get slow on large tables?

The database discards skipped rows server-side, but still has to read them. EF doesn't download them.

What's required for keyset pagination to give consistent results?

The cursor must identify a unique position, so include a unique tie-breaker column.

What's the main downside of keyset pagination?

Keyset navigates relative to a cursor: next and previous only.
