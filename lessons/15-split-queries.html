Split Queries & Cartesian Explosion

Including several collections in one query can multiply the rows the database returns. This lesson explains cartesian explosion and how split queries fix it, along with their trade-offs.

⏱ 25 min
🎯 Goal of this lesson

Understand cartesian explosion and learn when splitting one query into several is faster, and when it isn't.

Why it matters: Loading multiple collections in one query can multiply returned rows by orders of magnitude. Knowing the trade-off lets you choose based on measurements, not folklore.

By the end of this lesson you will be able to

  • Explain cartesian explosion and data duplication in single queries.
  • Use AsSplitQuery() and AsSingleQuery(), and set a global default.
  • Understand the consistency and round-trip trade-offs of split queries.
  • Choose the right approach for a given query.

The problem

Suppose Customer has two collections, Orders and Addresses. In a relational database, one query that loads both must JOIN them:

var customers = await db.Customers
    .Include(c => c.Orders)
    .Include(c => c.Addresses)
    .Where(c => c.Id < 100)
    .ToListAsync();

For a customer with 50 orders and 4 addresses, the JOIN produces 50 × 4 = 200 rows for that one customer. Every customer column is repeated in all 200 rows. Every order is repeated 4 times, and every address 50 times. Add a third collection and it multiplies again. This is cartesian explosion.

Even one collection duplicates data Include(o => o.Lines) repeats all of the order's columns in every line row. If the parent has large columns, such as the 2 KB Description on Product, that duplication alone can dominate network transfer.

EF warns you when a query loads multiple collections with single-query behaviour and no explicit choice:

warn: Microsoft.EntityFrameworkCore.Query[20504]
      Compiling a query which loads related collections for more than one collection navigation,
      either via 'Include' or through projection, but no 'QuerySplittingBehavior' has been configured...

The solution: AsSplitQuery

var customers = await db.Customers
    .Include(c => c.Orders)
    .Include(c => c.Addresses)
    .Where(c => c.Id < 100)
    .AsSplitQuery()
    .ToListAsync();
SELECT [c].* FROM [Customers] AS [c] WHERE [c].[Id] < 100 ORDER BY [c].[Id];

SELECT [o].*, [c].[Id] FROM [Customers] AS [c]
INNER JOIN [Orders] AS [o] ON [c].[Id] = [o].[CustomerId]
WHERE [c].[Id] < 100 ORDER BY [c].[Id];

SELECT [a].*, [c].[Id] FROM [Customers] AS [c]
INNER JOIN [Addresses] AS [a] ON [c].[Id] = [a].[CustomerId]
WHERE [c].[Id] < 100 ORDER BY [c].[Id];

Total rows are now 100 + (orders) + (addresses) instead of their product. Split queries also work with collections inside projections:

var dto = await db.Customers
    .Select(c => new { c.Name, Orders = c.Orders.Select(o => o.Total).ToList(), Cities = c.Addresses.Select(a => a.City).ToList() })
    .AsSplitQuery()
    .ToListAsync();

Trade-offs

AspectSingle query (default)Split query
Round trips11 + number of collection includes
Data duplicationHigh with collectionsNone
ConsistencyAtomic snapshot⚠ Data can change between queries unless you use a serializable or snapshot transaction
Skip/Take on the rootFine⚠ Before EF 10, a non-unique ordering could make child queries load data for different root rows. EF 10 adds the key to the ordering of every split query automatically. A deterministic ordering is still good practice.
Best whenReference navigations only, or one small collection; high-latency networksSeveral or large collections, wide parent rows
Buffering note On SQL Server without MARS (Multiple Active Result Sets), EF must buffer the results of all split queries except the last one in memory. That's usually fine, but worth knowing for very large results.

Setting a global default

options.UseSqlServer(connStr, sql =>
    sql.UseQuerySplittingBehavior(QuerySplittingBehavior.SplitQuery));

// Opt back into a single query where it's better:
var order = await db.Orders.Include(o => o.Customer).Include(o => o.Lines)
                           .AsSingleQuery().SingleAsync(o => o.Id == id);
How to decide Don't choose by rule. Measure both with realistic data and realistic network latency. A split query trades data volume for round trips. With 0.2 ms local latency, splitting almost always wins for multiple collections. With a 20 ms cross-region link, the extra round trips may cost more than the duplicated data. Often the best answer is neither: project only what you need (Lesson 11), so the duplication is a few narrow columns.

🔑 Key takeaways

  • Multiple collection includes in one query multiply rows (cartesian explosion).
  • AsSplitQuery trades extra round trips for no duplication. Measure both with realistic latency.
  • Split queries aren't one atomic snapshot. EF 10 keeps their ordering consistent automatically.
  • Often the best fix is a narrow projection instead of either strategy.

Exercise

🛠 Watch the rows multiply

  1. Add an Address entity (Id, CustomerId, City) and seed 5 addresses per customer.
  2. Run the double-include query for 100 customers as a single query. Log how many rows come back: run the SQL from ToQueryString() in your SQL tool.
  3. Switch to AsSplitQuery() and compare row counts and elapsed time.
  4. Rewrite it as a projection that only takes Order.Total and Address.City. Compare again.
What to expect

Single query: about 100 × 10 × 5 = 5,000 wide rows. Split: about 100 + 1,000 + 500 = 1,600 rows across three queries. The projection with split is the leanest of all.

Quiz

A query includes Orders (avg 20 per customer) and Tags (avg 10 per customer) for 50 customers. About how many rows does the single query return?

50 × 20 × 10 = 10,000 rows. The collections multiply each other.

What's a real risk of split queries?

Each query is a separate statement. Use a snapshot or serializable transaction if you need strict consistency.

When paging with Skip/Take and AsSplitQuery(), what must you ensure?

Each split query re-applies the paging. With a non-unique ordering, EF 9 and earlier could select different root rows in each query. EF 10 makes the ordering consistent automatically, but explicit unique ordering keeps results deterministic on every version.
