Efficient Saving & Bulk Operations

Reads get most of the attention, but slow writes hurt just as much. This lesson covers how SaveChanges batches work, set-based updates and deletes with ExecuteUpdate/ExecuteDelete, key generation strategies, and true bulk loading.

⏱ 35 min
🎯 Goal of this lesson

Learn to write data efficiently: batching, set-based updates and deletes, key generation strategies and true bulk loading.

Why it matters: Per-row saves and load-modify-save loops are slow and hold locks. Efficient writes keep imports, background jobs and APIs fast and reduce contention.

By the end of this lesson you will be able to

  • Avoid per-row round trips by letting EF batch changes.
  • Update and delete many rows without loading them, using ExecuteUpdateAsync and ExecuteDeleteAsync.
  • Use HiLo or sequences to reduce key-generation overhead.
  • Know when to reach for SqlBulkCopy, PostgreSQL COPY or a bulk library.

SaveChanges batching

SaveChanges collects every pending change and sends the commands in batches, many statements per round trip, inside one transaction.

❌ 1,000 round trips + 1,000 transactions 
foreach (var dto in incoming)
{
    db.Products.Add(Map(dto));
    await db.SaveChangesAsync();
}
✅ A handful of batched round trips 
db.Products.AddRange(incoming.Select(Map));
await db.SaveChangesAsync();

You can tune the batch size per provider:

options.UseSqlServer(connStr, sql => sql.MaxBatchSize(100));

The defaults are usually well chosen. Change them only after measuring.

Recent SaveChanges improvements (EF Core 7+)
  • When SaveChanges executes a single statement, EF no longer wraps it in an explicit transaction, which saves round trips.
  • On SQL Server, inserts use OUTPUT to return generated values in the same statement.
  • Triggers: SQL Server doesn't allow OUTPUT without INTO on tables with triggers. Declare them so EF uses a compatible, slightly slower SQL form: b.ToTable(t => t.HasTrigger("TR_Orders_Audit"));

Large imports: chunk and clear

Adding 1,000,000 entities to a single context makes the change tracker huge and DetectChanges slow. Process in chunks:

foreach (var chunk in rows.Chunk(5_000))
{
    db.Products.AddRange(chunk.Select(Map));
    await db.SaveChangesAsync();
    db.ChangeTracker.Clear();
}

If you change many tracked entities in a hot loop, db.ChangeTracker.AutoDetectChangesEnabled = false prevents repeated scans. Re-enable it, or call DetectChanges() manually, before saving.

ExecuteUpdate and ExecuteDelete

To change many rows, the traditional approach is load, modify, save: N rows loaded and N UPDATE statements. Since EF Core 7 you can issue a single set-based SQL statement directly from LINQ:

// Raise prices 10% in one category: one UPDATE, zero rows loaded
var affected = await db.Products
    .Where(p => p.CategoryId == categoryId)
    .ExecuteUpdateAsync(s => s
        .SetProperty(p => p.Price, p => p.Price * 1.10m)
        .SetProperty(p => p.Name, p => p.Name + " (new price)"));
UPDATE [p]
SET [p].[Price] = [p].[Price] * 1.10,
    [p].[Name] = [p].[Name] + N' (new price)'
FROM [Products] AS [p]
WHERE [p].[CategoryId] = @categoryId
// Purge old cancelled orders: one DELETE
await db.Orders
    .Where(o => o.Status == OrderStatus.Cancelled && o.PlacedUtc < cutoff)
    .ExecuteDeleteAsync();
New in EF Core 10: regular lambdas in ExecuteUpdate Before EF 10, the setters argument had to be an expression tree, which made conditional updates awkward. EF 10 accepts a normal lambda, so you can use plain if statements: 
await db.Products.Where(p => p.Id == id).ExecuteUpdateAsync(s =>
{
    s.SetProperty(p => p.Price, newPrice);
    if (newName is not null)
        s.SetProperty(p => p.Name, newName);
});
EF 10 also supports updating properties inside JSON columns mapped as complex types with ExecuteUpdate.
ExecuteUpdate/Delete bypass the change tracker
  • They run immediately, not at SaveChanges, and outside its transaction. Wrap them in an explicit transaction if they must commit atomically with other changes.
  • Already-tracked entities are not updated in memory, so they're now stale.
  • SaveChanges interceptors, and overrides such as audit fields set in SaveChanges, don't run. Set audit columns in the SetProperty call yourself.
  • Cascade deletes configured only in EF (not in the database) don't happen.

Key generation: IDENTITY vs HiLo vs sequences

With IDENTITY columns, the database generates keys, and EF reads them back. With HiLo, EF reserves a block of keys from a database sequence and assigns them client-side. Keys are then known before SaveChanges, and EF fetches a new block only occasionally.

modelBuilder.Entity<Order>()
    .Property(o => o.Id)
    .UseHiLo("OrderHiLoSequence");      // SQL Server sequence, blocks of 10 by default

// or model-wide
modelBuilder.UseHiLo();

HiLo is helpful when you need ids before saving, for example to build related graphs or publish messages, and in some high-volume insert scenarios. Its downsides are gaps in key values and a database sequence to manage. For most apps IDENTITY is fine. Measure before switching.

True bulk loading

For hundreds of thousands of rows, even batched INSERT statements are slow compared with the database's native bulk path:

OptionNotes
SqlBulkCopy (SQL Server)Built into Microsoft.Data.SqlClient and extremely fast. You map columns yourself, and it bypasses EF.
Npgsql binary COPY (PostgreSQL)conn.BeginBinaryImport("COPY ... FROM STDIN (FORMAT BINARY)")
Third-party: EFCore.BulkExtensions, linq2db.EntityFrameworkCore, Entity Framework ExtensionsBulk insert, update, merge and upsert on top of your EF model. Check the licences: some are commercial or dual-licensed.
Set-based SQLINSERT INTO ... SELECT ... through ExecuteSqlAsync when data already lives in the database.
 
// SqlBulkCopy sketch using the EF connection
var conn = (SqlConnection)db.Database.GetDbConnection();   // Microsoft.Data.SqlClient
if (conn.State != ConnectionState.Open) await conn.OpenAsync();   // EF may already have it open
using var bulk = new SqlBulkCopy(conn) { DestinationTableName = "Products", BatchSize = 10_000 };
bulk.ColumnMappings.Add(nameof(Product.Sku), "Sku");
bulk.ColumnMappings.Add(nameof(Product.Name), "Name");
// ...
await bulk.WriteToServerAsync(dataTableOrDataReader);

🔑 Key takeaways

  • Never call SaveChanges in a loop. Let EF batch changes, and chunk very large imports.
  • ExecuteUpdateAsync/ExecuteDeleteAsync change many rows in one statement without loading them.
  • Execute* methods bypass the change tracker, SaveChanges interceptors and SaveChanges' transaction.
  • For hundreds of thousands of rows, use the database's bulk path (SqlBulkCopy, COPY).

Exercise

🛠 Four ways to write

Insert 50,000 products and time each approach:

  1. Add + SaveChanges per row
  2. AddRange + one SaveChanges
  3. AddRange in chunks of 5,000 with ChangeTracker.Clear()
  4. SqlBulkCopy

Then mark all products in category 1 as discounted, first by load-modify-save, then with ExecuteUpdateAsync.

What to expect

Per-row saves typically take minutes. Batching takes seconds. Bulk copy takes well under a second to a couple of seconds. ExecuteUpdateAsync beats load-modify-save by orders of magnitude on large sets, because no rows cross the network.

Quiz

When does ExecuteDeleteAsync() run its SQL?

Execute* methods run immediately and bypass the change tracker.

You call ExecuteUpdateAsync on products that are also tracked by the context. What happens to the tracked instances?

The change tracker isn't aware of bulk updates. Reload the entities or clear the tracker if you keep using them.

What's the main reason to declare HasTrigger() on SQL Server tables that have triggers?

Without it, SaveChanges fails on tables with triggers (EF Core 7+).
