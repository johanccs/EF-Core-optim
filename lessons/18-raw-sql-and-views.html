Raw SQL, Views & Stored Procedures

LINQ covers most queries, but sometimes hand-written SQL is the best tool: window functions, provider-specific features, hints, or tuned reporting queries. This lesson covers dropping down to SQL safely while keeping EF's benefits.

⏱ 30 min
🎯 Goal of this lesson

Learn to use raw SQL safely when LINQ isn't the best tool, while keeping EF's composition, materialization and parameterization.

Why it matters: Some queries are best expressed in SQL. Doing it wrong opens SQL injection holes or loses composability. Doing it right gives you full database power safely.

By the end of this lesson you will be able to

  • Query entities with FromSql and compose LINQ on top.
  • Query unmapped types and scalars with Database.SqlQuery<T>.
  • Execute commands with ExecuteSqlAsync.
  • Map views, table-valued functions and keyless entities.
  • Avoid SQL injection.

FromSql: entities from SQL

FromSql (EF Core 7+) takes an interpolated string and turns every interpolated value into a DbParameter. It's safe by construction.

var minPrice = 50m;
var products = await db.Products
    .FromSql($"SELECT * FROM Products WITH (INDEX(IX_Products_Price)) WHERE Price > {minPrice}")
    .AsNoTracking()
    .ToListAsync();

Composing LINQ over SQL

If the SQL is a composable SELECT, EF wraps it in a subquery so you can keep filtering, sorting, projecting and including:

var top = await db.Products
    .FromSql($"SELECT * FROM dbo.SearchProducts({term})")   // table-valued function
    .Where(p => p.Price < 100)
    .OrderBy(p => p.Name)
    .Select(p => new { p.Id, p.Name })
    .Take(20)
    .ToListAsync();
Rules for FromSql on entity types
  • The SQL must return all mapped columns of the entity, with matching names.
  • Stored procedures (EXEC ...) can't be composed. Call .AsAsyncEnumerable() or .ToListAsync() right after FromSql, and do any further work in memory.
  • On SQL Server, don't end composable SQL with a semicolon.

SQL injection: the one rule

❌ Injectable 
// string concatenation / interpolation into a RAW API
db.Products.FromSqlRaw(
    "SELECT * FROM Products WHERE Name = '" + name + "'");

db.Products.FromSqlRaw(
    $"SELECT * FROM Products WHERE Name = '{name}'");
✅ Parameterized 
db.Products.FromSql(
    $"SELECT * FROM Products WHERE Name = {name}");

db.Products.FromSqlRaw(
    "SELECT * FROM Products WHERE Name = {0}", name);

FromSqlRaw and ExecuteSqlRaw exist for dynamic SQL structure, such as table or column names you can't parameterize. Validate those identifiers against an allow-list, and still pass values as parameters. Since EF 10, a built-in analyzer warns when you concatenate strings inside a raw SQL call.

SqlQuery: unmapped types and scalars

EF Core 8+ can materialize any type from SQL. It doesn't need to be in your model:

public record SalesByMonth(int Year, int Month, decimal Revenue, int Orders);

var report = await db.Database.SqlQuery<SalesByMonth>($"""
    SELECT YEAR(PlacedUtc) AS [Year], MONTH(PlacedUtc) AS [Month],
           SUM(Total) AS Revenue, COUNT(*) AS Orders
    FROM Orders
    WHERE PlacedUtc >= {from}
    GROUP BY YEAR(PlacedUtc), MONTH(PlacedUtc)
    """).ToListAsync();

// Scalars: name the output column "Value" if you compose LINQ on top
var ids = await db.Database
    .SqlQuery<int>($"SELECT Id AS Value FROM Orders WHERE Status = 0")
    .Where(id => id > lastId)
    .ToListAsync();

ExecuteSql: commands

var rows = await db.Database.ExecuteSqlAsync(
    $"UPDATE Products SET Price = Price * {factor} WHERE CategoryId = {categoryId}");

await db.Database.ExecuteSqlAsync($"EXEC dbo.RebuildSearchIndex @Full = {true}");

Prefer ExecuteUpdateAsync (Lesson 16) for set-based updates expressible in LINQ. It's type-safe and refactor-friendly. Use ExecuteSqlAsync for everything else.

Views and keyless entities

Map a database view, or any read-only result shape, as a keyless entity type:

public class CustomerSalesView
{
    public int CustomerId { get; set; }
    public string Name { get; set; } = "";
    public decimal LifetimeSpend { get; set; }
    public int OrderCount { get; set; }
}

modelBuilder.Entity<CustomerSalesView>(b =>
{
    b.HasNoKey();
    b.ToView("vw_CustomerSales");           // EF won't try to create it in migrations
});

var vips = await db.Set<CustomerSalesView>()
    .Where(v => v.LifetimeSpend > 10_000)
    .OrderByDescending(v => v.LifetimeSpend)
    .ToListAsync();

Create the view itself in a migration with migrationBuilder.Sql("CREATE VIEW ..."). For SQL Server, an indexed view can pre-compute expensive aggregates, and an Azure SQL / PostgreSQL materialized view plays the same role.

Mapping functions

// Table-valued function → composable IQueryable
public IQueryable<Product> SearchProducts(string term) => FromExpression(() => SearchProducts(term));

modelBuilder.HasDbFunction(typeof(ShopContext).GetMethod(nameof(SearchProducts), new[] { typeof(string) })!);

// Scalar function usable inside LINQ
[DbFunction("fn_Discount", "dbo")]
public static decimal Discount(decimal price, int customerTier) => throw new NotSupportedException();

var q = db.Products.Select(p => new { p.Name, Final = ShopContext.Discount(p.Price, tier) });

When to use raw SQL

  • Window functions, CTEs, recursive queries, PIVOT, provider-specific operators. Check first, though: EF translates more each release.
  • Query hints and tuned reporting queries you've already optimized in SQL.
  • Calling existing stored procedures.
  • Not as a first resort. LINQ is type-safe, refactorable and composable.

🔑 Key takeaways

  • FromSql/ExecuteSql parameterize interpolated values, so they're safe by construction.
  • FromSqlRaw is for dynamic structure only. Allow-list identifiers and never concatenate values.
  • SqlQuery<T> materializes unmapped types and scalars. Keyless entities map views.
  • Composable SELECTs can be extended with LINQ. Stored procedures can't.

🛠 Build a report two ways

  1. Write the "top 10 customers by spend in the last 90 days" report in LINQ and inspect the SQL.
  2. Write it as a view vw_CustomerSpend90d, map it as a keyless entity and query it.

LINQ version 
var since = DateTime.UtcNow.AddDays(-90);
var top = await db.Customers
    .Select(c => new { c.Id, c.Name, Spend = c.Orders.Where(o => o.PlacedUtc >= since).Sum(o => o.Total) })
    .OrderByDescending(x => x.Spend)
    .Take(10)
    .ToListAsync();

Quiz

Is FromSql($"... WHERE Name = {name}") safe from SQL injection?

FromSql and ExecuteSql take a FormattableString and parameterize every hole.

Which API materializes an arbitrary, unmapped type such as a report record?

SqlQuery<T> (EF Core 8+) supports any type with matching column names, plus scalars.

What's true about FromSql with a stored procedure call (EXEC ...)?

EF can't wrap EXEC in a subquery, so composition must happen client-side.
