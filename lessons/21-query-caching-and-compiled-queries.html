Query Caching, Parameters & Compiled Queries

Translating LINQ into SQL is the most expensive thing EF does in-process. EF caches the result, but only if your queries cooperate. This lesson covers how the query cache works, how to pollute it by accident, how collection parameters are translated, and when compiled queries help.

⏱ 35 min
🎯 Goal of this lesson

Understand EF's query cache and the database plan cache, how to avoid polluting them, and when compiled queries pay off.

Why it matters: Query compilation is EF's most expensive in-process step. A polluted cache silently burns CPU on both the app server and the database.

By the end of this lesson you will be able to

  • Explain the two caches involved: EF's query cache and the database plan cache.
  • Avoid query cache pollution from constants in dynamically built expressions.
  • Control parameterization with EF.Constant and EF.Parameter.
  • Understand how collections in Contains are translated, and the EF Core 10 changes.
  • Use EF.CompileAsyncQuery on hot paths.

Two caches

  1. EF's compiled query cache (in your process). Key: the expression tree shape. Value: the generated SQL plus the materializer. A miss means full LINQ translation, which costs anywhere from microseconds to milliseconds of CPU.
  2. The database's plan cache. Key: the SQL text. A miss means the optimizer compiles a new execution plan, which costs CPU on the database server.

Both caches work best when the same query shape produces the same SQL text with different parameter values.

Constants vs parameters

EF decides from the expression tree:

  • Captured variables (closures) become parameters: Where(p => p.Id == id) → WHERE [p].[Id] = @__id_0
  • Literals become constants inlined in the SQL: Where(p => p.Status == 1) → WHERE [p].[Status] = 1

Literals in hand-written LINQ are fine, because the shape never changes. The problem appears when you build expressions dynamically:

❌ New query (and plan) per value 
static Expression<Func<Product, bool>>
    PriceAbove(decimal min)
{
    var p = Expression.Parameter(typeof(Product));
    var body = Expression.GreaterThan(
        Expression.Property(p, nameof(Product.Price)),
        Expression.Constant(min));     // literal!
    return Expression.Lambda<Func<Product, bool>>(body, p);
}
// WHERE [p].[Price] > 10.0
// WHERE [p].[Price] > 10.5   ← different SQL each time
✅ One cached query 
static Expression<Func<Product, bool>>
    PriceAbove(decimal min)
{
    // Let the compiler create the closure for you
    return p => p.Price > min;
}
// WHERE [p].[Price] > @__min_0

If you really have to build trees by hand, for a generic filter or a search builder, wrap values in a closure-like object so EF sees member access rather than a constant:

var holder = new { Value = min };
var valueExpr = Expression.Property(Expression.Constant(holder), "Value");   // parameterized by EF

Forcing the choice: EF.Constant and EF.Parameter

// Force a parameter to be inlined as a constant (EF 8+).
// Useful when the value is low-cardinality and a value-specific plan helps.
var q1 = db.Orders.Where(o => o.Status == EF.Constant(status));

// Force a literal to be sent as a parameter (EF 9+)
var q2 = db.Orders.Where(o => o.Total > EF.Parameter(100m));
Check your hit rate The Microsoft.EntityFrameworkCore metrics (Lesson 19) include the compiled query cache hit rate. In steady state it should be close to 100%. A persistently low value means something is generating unique query shapes.

Collections: Contains translation

A very common query is "rows whose id is in this list":

int[] ids = [1, 7, 42, 99];
var orders = await db.Orders.Where(o => ids.Contains(o.Id)).ToListAsync();

Translation has changed across versions, and it matters for both caches:

VersionDefault SQLNotes
EF Core ≤ 7WHERE [Id] IN (1, 7, 42, 99)Constants: a different SQL text for every distinct list, which pollutes the plan cache.
EF Core 8–9WHERE [Id] IN (SELECT [value] FROM OPENJSON(@__ids_0) ...)One JSON parameter and one SQL text, but the optimizer can't see how many values there are, which sometimes produces poor plans.
EF Core 10WHERE [Id] IN (@ids1, @ids2, @ids3, @ids4)Multiple scalar parameters. The optimizer gets cardinality information, and EF pads the parameter count to limit the number of distinct SQL shapes.

You can override the default globally or per query:

// Globally (EF 10)
options.UseSqlServer(connStr, o => o.UseParameterizedCollectionMode(ParameterTranslationMode.Parameter));  // JSON array

// Per query
db.Orders.Where(o => EF.Constant(ids).Contains(o.Id));    // inline constants
db.Orders.Where(o => EF.Parameter(ids).Contains(o.Id));   // single JSON parameter
Very large lists SQL Server allows at most about 2,100 parameters per command. For lists with thousands of values, use the single JSON-parameter mode, a table-valued parameter through raw SQL, or bulk-insert the ids into a temp table and JOIN.

Compiled queries

Even with a cache hit, EF still compares the incoming expression tree with cached trees and extracts parameters. For extremely hot queries you can skip that work with an explicitly compiled query:

public class ShopQueries
{
    // Compile once: store in a static field
    public static readonly Func<ShopContext, int, Task<Product?>> ProductById =
        EF.CompileAsyncQuery((ShopContext db, int id) =>
            db.Products.AsNoTracking().FirstOrDefault(p => p.Id == id));

    public static readonly Func<ShopContext, int, IAsyncEnumerable<Order>> OrdersForCustomer =
        EF.CompileAsyncQuery((ShopContext db, int customerId) =>
            db.Orders.AsNoTracking().Where(o => o.CustomerId == customerId).OrderBy(o => o.Id));
}

// Usage
var product = await ShopQueries.ProductById(db, 42);
await foreach (var o in ShopQueries.OrdersForCustomer(db, 7)) { /* ... */ }
  • The gain is CPU per execution, typically a few microseconds. It's visible only for very hot, simple queries at high throughput.
  • Compiled queries are less flexible: no dynamic composition after compilation, and a fixed parameter list.
  • Always benchmark (Lesson 25) before adopting them widely.

Dynamic queries and shape explosion

Conditional composition is normal and fine, but each combination of applied filters is a distinct shape. Ten optional filters can produce up to 210 = 1,024 shapes. That's usually acceptable. Just don't add value-dependent shapes on top, like the constant problem above.

IQueryable<Product> q = db.Products;
if (filter.CategoryId is int c) q = q.Where(p => p.CategoryId == c);      // parameter: good
if (filter.MaxPrice is decimal m) q = q.Where(p => p.Price <= m);         // parameter: good

  2. Fix it using the closure-holder technique and confirm there's one SQL text.
  3. Benchmark db.Products.FirstOrDefaultAsync(p => p.Id == id) against the compiled ProductById (Lesson 25 shows the harness).
Fixed helper 
public static IQueryable<T> WhereEquals<T>(this IQueryable<T> source, string property, object value)
{
    var param = Expression.Parameter(typeof(T), "x");
    var member = Expression.Property(param, property);
    var holder = Activator.CreateInstance(typeof(ValueHolder<>).MakeGenericType(member.Type), value)!;
    var valueExpr = Expression.Property(Expression.Constant(holder), "Value");
    var body = Expression.Equal(member, valueExpr);
    return source.Where(Expression.Lambda<Func<T, bool>>(body, param));
}

public sealed class ValueHolder<TValue>(TValue value) { public TValue Value { get; } = value; }

Quiz

Where(p => p.Price > min), where min is a local variable, generates…

Captured variables become parameters, so the query shape is stable across values.

What's the risk of using Expression.Constant(value) in dynamically built filters?

Constants are inlined, so every value is a new SQL text and a new compilation.

How does EF Core 10 translate ids.Contains(o.Id) on SQL Server by default?

EF 10 switched the default to multiple parameters, which gives the optimizer cardinality information. The mode is configurable.
