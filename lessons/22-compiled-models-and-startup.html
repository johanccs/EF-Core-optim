Compiled Models, Startup & Native AOT

The first request after a deploy is often the slowest. EF Core has to build its model and compile its first queries. For large models this takes seconds. This lesson covers compiled models, warm-up strategies, and EF's path toward Native AOT.

⏱ 30 min
🎯 Goal of this lesson

Learn to reduce startup and first-request latency with compiled models and warm-up, and understand EF's path to Native AOT.

Why it matters: Cold starts hurt autoscaling, serverless and deployments. With large models, model building alone can take seconds on every start.

By the end of this lesson you will be able to

  • Measure where startup time goes.
  • Generate and use a compiled model with dotnet ef dbcontext optimize.
  • Automate compiled model generation in the build (EF 9+).
  • Warm up EF at startup, and understand precompiled queries and Native AOT support.

What happens on the first query

  1. Model building: EF scans your entity types, runs every convention, applies OnModelCreating and validates the result. This happens once per context type per process.
  2. Service provider creation: EF builds its internal DI container. It's cached, but costs time on first use.
  3. Query compilation for each distinct query, as covered in Lesson 21.
  4. First connection: the pool is empty, so TLS and login handshakes happen.

For a model with 20 entities this takes a few hundred milliseconds. With 500+ entities, model building alone can take several seconds. That hurts serverless cold starts, autoscaling, and every developer's F5.

var sw = Stopwatch.StartNew();
await using (var db = new ShopContext(options))
{
    _ = db.Model;                                        // forces model building
    Console.WriteLine($"Model built: {sw.ElapsedMilliseconds} ms");
    await db.Customers.AnyAsync();
    Console.WriteLine($"First query: {sw.ElapsedMilliseconds} ms");
}

Compiled models

A compiled model is generated C# source that constructs the finished model directly, skipping conventions and model building at runtime.

dotnet ef dbcontext optimize --output-dir CompiledModels --namespace Shop.Data.CompiledModels

This generates classes such as ShopContextModel. Wire it up:

options.UseSqlServer(connStr)
       .UseModel(Shop.Data.CompiledModels.ShopContextModel.Instance);
EF Core 9+: less ceremony
  • Auto-discovery: if the compiled model is in the same assembly as the context, EF finds and uses it without UseModel.
  • MSBuild integration: add the Microsoft.EntityFrameworkCore.Tasks package and set <EFOptimizeContext>true</EFOptimizeContext> in the project file. The compiled model is then regenerated on build, by default for Release builds, so it can't go stale.
<PropertyGroup>
  <EFOptimizeContext>true</EFOptimizeContext>
</PropertyGroup>
<ItemGroup>
  <PackageReference Include="Microsoft.EntityFrameworkCore.Tasks" Version="10.0.*" PrivateAssets="all" />
</ItemGroup>
Trade-offs
  • If you generate it manually, you must regenerate after every model change, or the runtime model won't match your code. Automate it in the build or CI.
  • The generated code is large for big models, so compile time increases.
  • A few features have restrictions with compiled models. Check the current docs for your version.
  • For small models the gain is small. Measure first.

Warm-up

Even with a compiled model, the first execution of each query compiles it. Move that cost out of user requests by warming up during startup, before the instance receives traffic:

var app = builder.Build();

using (var scope = app.Services.CreateScope())
{
    var db = scope.ServiceProvider.GetRequiredService<ShopContext>();
    _ = db.Model;                                   // model (or compiled model) loaded
    await db.Database.CanConnectAsync();            // first physical connection, pool primed

    // Optionally execute your hottest queries once to fill the query cache
    _ = await db.Products.AsNoTracking().Where(p => p.Id == 0).Select(p => p.Id).ToListAsync();
}

app.Run();

Combine this with a readiness probe in Kubernetes or Azure App Service health checks, so the load balancer only routes traffic after warm-up finishes.

Precompiled queries and Native AOT

Native AOT compiles your app to native code with no JIT, giving fast startup and a small memory footprint. Classic EF can't work this way, because LINQ query translation relies on runtime code generation. Starting with EF 9, EF can precompile queries at publish time: it finds your LINQ queries, translates them ahead of time, and uses C# interceptors to replace them with the precompiled versions.

dotnet ef dbcontext optimize --precompile-queries --nativeaot
Status: experimental Precompiled queries and Native AOT support were introduced as experimental in EF 9. Only statically analyzable queries can be precompiled, so dynamic composition across methods may not be supported. Check the release notes for your EF version before relying on this in production. For most server apps, compiled models plus warm-up give most of the startup benefit with no restrictions.

Startup checklist

  • Measure: time to model built, time to first query, time to first request.
  • Large model (100+ entity types)? Use a compiled model, generated in the build.
  • Warm up the connection and hot queries before taking traffic.
  • Don't run Database.Migrate() at startup in production (Lesson 14). It adds latency and risk.
  • Serverless or scale-to-zero? Consider ReadyToRun or Native AOT for the whole app, and evaluate precompiled queries.

What to expect

With hundreds of entity types, model building drops from seconds to tens of milliseconds with a compiled model. The exact numbers depend on your hardware and model complexity.

Quiz

What does a compiled model eliminate at runtime?

It replaces model building with generated code. Queries still compile on first use, unless they're precompiled.

What's the main risk of a manually generated compiled model?

Automate generation, for example with EFOptimizeContext in EF 9+, to avoid drift.

Why can't classic EF Core queries run under Native AOT?

Precompiled queries (experimental since EF 9) translate queries at publish time to work around this.
