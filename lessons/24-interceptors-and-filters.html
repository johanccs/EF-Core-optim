Interceptors, Query Filters & Conventions

Cross-cutting concerns such as soft delete, multi-tenancy, auditing, query hints and monitoring belong in one place, not copied into every query. This lesson covers EF's extension points and how to use them without adding overhead.

⏱ 35 min
🎯 Goal of this lesson

Learn to implement cross-cutting concerns once (auditing, soft delete, multi-tenancy, query hints, monitoring) using interceptors, query filters and conventions.

Why it matters: Copy-pasted cross-cutting logic drifts and causes bugs and data leaks. Centralized extension points keep it consistent, but they run on every operation, so they must stay cheap.

By the end of this lesson you will be able to

  • Write command, SaveChanges and materialization interceptors.
  • Use global query filters for soft delete and tenancy, including EF 10 named filters.
  • Index for query filters so they stay fast.
  • Write a custom model-building convention.

Interceptors

Interceptors let you observe and modify EF operations. The main kinds:

Interface / base classInterceptsTypical use
DbCommandInterceptorCommand creation and executionSlow-query logging, query hints, command counting
DbConnectionInterceptorOpening and closing connectionsSetting session context (e.g. SESSION_CONTEXT for row-level security), access tokens
DbTransactionInterceptorTransactionsDiagnostics
SaveChangesInterceptorSaveChangesAudit fields, domain events, outbox
IMaterializationInterceptorEntity instance creationInjecting services, post-load initialization
IQueryExpressionInterceptorThe LINQ expression tree before compilationRewriting queries, enforcing rules
Interceptors are on the hot path Command interceptors run for every command. Keep them cheap. No I/O, no heavy allocation, no locks. Register stateless interceptors as singletons and add them once with AddInterceptors.

Example: audit fields with SaveChangesInterceptor

public interface IAuditable { DateTime CreatedUtc { get; set; } DateTime? ModifiedUtc { get; set; } }

public sealed class AuditInterceptor(TimeProvider clock) : SaveChangesInterceptor
{
    // Override BOTH: SaveChanges() calls the sync hook, SaveChangesAsync() the async one.
    public override InterceptionResult<int> SavingChanges(DbContextEventData eventData, InterceptionResult<int> result)
    {
        Stamp(eventData.Context);
        return result;
    }

    public override ValueTask<InterceptionResult<int>> SavingChangesAsync(
        DbContextEventData eventData, InterceptionResult<int> result, CancellationToken ct = default)
    {
        Stamp(eventData.Context);
        return ValueTask.FromResult(result);
    }

    private void Stamp(DbContext? context)
    {
        if (context is null) return;
        var now = clock.GetUtcNow().UtcDateTime;
        foreach (var e in context.ChangeTracker.Entries<IAuditable>())
        {
            if (e.State == EntityState.Added) e.Entity.CreatedUtc = now;
            if (e.State == EntityState.Modified) e.Entity.ModifiedUtc = now;
        }
    }
}

Example: query hints by tag

Combine a query tag (Lesson 19) with a command interceptor to add a hint to specific queries only, for example to fight parameter sniffing:

public sealed class RecompileHintInterceptor : DbCommandInterceptor
{
    public const string Tag = "-- hint:recompile";

    public override InterceptionResult<DbDataReader> ReaderExecuting(
        DbCommand command, CommandEventData eventData, InterceptionResult<DbDataReader> result)
    {
        AddHint(command);
        return result;
    }

    public override ValueTask<InterceptionResult<DbDataReader>> ReaderExecutingAsync(
        DbCommand command, CommandEventData eventData, InterceptionResult<DbDataReader> result, CancellationToken ct = default)
    {
        AddHint(command);
        return ValueTask.FromResult(result);
    }

    private static void AddHint(DbCommand command)
    {
        // TagWith("hint:recompile") makes EF emit "-- hint:recompile" as the first line
        if (command.CommandText.StartsWith(Tag, StringComparison.Ordinal))
            command.CommandText += " OPTION (RECOMPILE)";
    }
}

var rows = await db.Orders.TagWith("hint:recompile").Where(o => o.CustomerId == id).ToListAsync();

Global query filters

A query filter is a predicate EF adds automatically to every query on an entity type, including Includes and navigations:

public class ShopContext(DbContextOptions<ShopContext> options, ITenantProvider tenant) : DbContext(options)
{
    private readonly int _tenantId = tenant.CurrentTenantId;

    protected override void OnModelCreating(ModelBuilder b)
    {
        b.Entity<Order>().HasQueryFilter(o => !o.IsDeleted && o.TenantId == _tenantId);
    }
}

// Bypass when needed (admin screens, data fixes):
var all = await db.Orders.IgnoreQueryFilters().ToListAsync();

The context field _tenantId is read per query and sent as a parameter, so the query cache still works. With pooling, use the factory pattern from Lesson 20 instead of constructor injection.

New in EF Core 10: named query filters Before EF 10, an entity type could have only one filter. Calling HasQueryFilter again replaced it, and IgnoreQueryFilters() was all or nothing. EF 10 lets you name filters and disable them selectively: 
b.Entity<Order>()
 .HasQueryFilter("SoftDelete", o => !o.IsDeleted)
 .HasQueryFilter("Tenant", o => o.TenantId == _tenantId);

// Show deleted orders, but still only for this tenant
var bin = await db.Orders.IgnoreQueryFilters(["SoftDelete"]).Where(o => o.IsDeleted).ToListAsync();

Indexing for filters

Every query on a filtered entity now includes the filter predicate, so your indexes must account for it:

  • Multi-tenancy: put TenantId first in your composite indexes: (TenantId, CustomerId, PlacedUtc).
  • Soft delete: use filtered indexes that only contain live rows: HasIndex(o => o.PlacedUtc).HasFilter("[IsDeleted] = 0"). They're smaller and match the predicate.
Filters and required navigations If Customer is soft-deleted and Order.Customer is a required navigation, an Include(o => o.Customer) uses an INNER JOIN, and the customer's filter makes those orders disappear from the results. Either filter both sides consistently or make the navigation optional. EF warns about this in the model validation logs.

Custom conventions

Conventions let you encode team rules once. For example, "every entity with a TenantId gets an index on it":

public sealed class TenantIndexConvention : IModelFinalizingConvention
{
    public void ProcessModelFinalizing(IConventionModelBuilder modelBuilder, IConventionContext<IConventionModelBuilder> context)
    {
        foreach (var entityType in modelBuilder.Metadata.GetEntityTypes())
        {
            if (entityType.BaseType is not null) continue;           // root types only
            var tenant = entityType.FindProperty("TenantId");
            if (tenant is not null)
                entityType.Builder.HasIndex(new[] { tenant });
        }
    }
}

protected override void ConfigureConventions(ModelConfigurationBuilder configurationBuilder)
{
    configurationBuilder.Conventions.Add(_ => new TenantIndexConvention());
}

You can also remove conventions you don't want. For example, configurationBuilder.Conventions.Remove(typeof(ForeignKeyIndexConvention)); stops automatic FK indexes when you manage all indexes yourself. Do this only deliberately.

🔑 Key takeaways

  • Interceptors centralize cross-cutting logic but run on every operation. Keep them cheap, and override both sync and async hooks.
  • Global query filters implement soft delete and tenancy. EF 10 adds named filters you can disable individually.
  • Index for your filters: tenant column first, filtered indexes for live rows.
  • Custom conventions encode team rules once, model-wide.

Soft-delete interceptor sketch (async hook shown; override the sync SavingChanges too) 
public override ValueTask<InterceptionResult<int>> SavingChangesAsync(DbContextEventData e, InterceptionResult<int> r, CancellationToken ct = default)
{
    foreach (var entry in e.Context!.ChangeTracker.Entries<ISoftDeletable>().Where(x => x.State == EntityState.Deleted))
    {
        entry.State = EntityState.Modified;
        entry.Entity.IsDeleted = true;
    }
    return ValueTask.FromResult(r);
}

Quiz

Where is the tenant id from a context field evaluated in a global query filter?

EF parameterizes context members referenced in filters, so each query uses the current context's value.

What does EF Core 10's named query filters feature enable?

Before EF 10 there was one filter per entity, and ignoring was all or nothing.

Which index best supports a multi-tenant query: WHERE TenantId = @t AND CustomerId = @c ORDER BY PlacedUtc DESC?

Equality columns first (TenantId, CustomerId), then the sort column.
