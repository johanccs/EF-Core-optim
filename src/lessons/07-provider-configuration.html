Provider-Specific Configuration

EF Core's behaviour depends heavily on its database provider. Every option on the provider builder changes compatibility, translations, resiliency or performance. This lesson walks through the options for SQL Server/Azure SQL, PostgreSQL and SQLite that matter most.

⏱ 35 min
🎯 Goal of this lesson

Configure your database provider deliberately instead of accepting defaults: know which provider-level switches exist, what each one changes in the generated SQL or runtime behaviour, and which provider quirks to plan for.

Why it matters: the same LINQ query can produce different SQL, or fail, depending on provider settings like the compatibility level or PostgreSQL version. Many production surprises, such as timestamp errors on PostgreSQL, unsupported functions on older SQL Server versions, or SQLite's limited ALTER TABLE support, are avoided by configuring the provider correctly from day one.

By the end of this lesson you will be able to

  • Use the provider options builder (UseSqlServer(conn, sql => …)) confidently.
  • Configure SQL Server and Azure SQL: compatibility level, timeouts, batching, retries, migrations.
  • Configure PostgreSQL with Npgsql: server version, enums, date/time behaviour, naming.
  • Know SQLite's main limitations and settings.

Two levels of options

EF configuration has general options on DbContextOptionsBuilder (logging, tracking behaviour, interceptors) and provider options inside the provider's own builder:

```csharp options .UseSqlServer(connStr, sql => // ← provider options builder { sql.CommandTimeout(30); sql.EnableRetryOnFailure(); }) .UseQueryTrackingBehavior(QueryTrackingBehavior.NoTracking) // ← general option .AddInterceptors(new SlowQueryInterceptor()); ```

SQL Server and Azure SQL

```csharp options.UseSqlServer(connStr, sql => { sql.CommandTimeout(30); // seconds per command sql.EnableRetryOnFailure(5, TimeSpan.FromSeconds(10), null); // transient fault handling (Lesson 17) sql.MaxBatchSize(100); // statements per SaveChanges round trip (Lesson 16) sql.UseQuerySplittingBehavior(QuerySplittingBehavior.SplitQuery); // Lesson 15 sql.UseCompatibilityLevel(160); // match your server (160 = SQL Server 2022) sql.MigrationsAssembly("Shop.Migrations"); // Lesson 5 sql.MigrationsHistoryTable("__EFMigrationsHistory", "dbo"); }); // EF 9+: target Azure SQL explicitly instead of on-premises SQL Server options.UseAzureSql(connStr, sql => sql.EnableRetryOnFailure()); ```
OptionEffect
UseCompatibilityLevel(n)Tells EF which SQL features it may use. For example, OPENJSON-based translations need level 130+. If your database runs at an older level than EF assumes, some queries fail at runtime with syntax errors. Set it to your database's compatibility level.
CommandTimeout(s)The maximum duration per command (default 30 s). Raise it for specific long operations with db.Database.SetCommandTimeout(...) rather than globally.
EnableRetryOnFailureRetries known transient errors. Essential on Azure SQL. Changes how manual transactions must be written.
MaxBatchSize / MinBatchSizeTune SaveChanges batching. Leave the defaults unless you've measured.
UseParameterizedCollectionMode (EF 10)How Contains over a collection is translated (Lesson 21).
UseAzureSql (EF 9+)Enables Azure-SQL-specific defaults and features.
Newer SQL Server features EF 10 supports the native json data type and the vector type (SqlVector<float> with EF.Functions.VectorDistance, for AI similarity search) on Azure SQL and SQL Server 2025. With UseAzureSql, or a compatibility level of 170 or higher, EF 10 defaults to the json type for JSON-mapped data. Your next migration will convert existing nvarchar JSON columns to json. Opt out by setting the column type to nvarchar(max) explicitly, or by configuring a lower compatibility level.

PostgreSQL (Npgsql)

```csharp var dsb = new NpgsqlDataSourceBuilder(connStr); var dataSource = dsb.Build(); builder.Services.AddDbContext(o => o .UseNpgsql(dataSource, npg => { npg.SetPostgresVersion(16, 0); // allow SQL features of your server version npg.EnableRetryOnFailure(); npg.MapEnum("order_status"); // native PostgreSQL enum (Npgsql EF 9+) npg.CommandTimeout(30); }) .UseSnakeCaseNamingConvention()); // EFCore.NamingConventions package ```
TopicWhat to know
Date/timeSince Npgsql 6, DateTime maps to timestamp with time zone, and writing a DateTime whose Kind isn't Utc throws. Store UTC everywhere (DateTime.UtcNow). Use timestamp without time zone only for genuinely local times. Consider NodaTime (npg.UseNodaTime()) for precise date/time semantics.
NamingPostgreSQL folds unquoted identifiers to lower case. Snake-case naming (order_lines.unit_price) makes hand-written SQL much nicer.
Server versionSetPostgresVersion lets EF use newer SQL features. Set it to the oldest version you deploy to.
TypesNative arrays, jsonb, ranges and full-text search are first-class. Index them with GIN or GiST indexes, configured with HasMethod("gin").
ConcurrencyUse the xmin system column as a row version (Lesson 17).

SQLite

```csharp options.UseSqlite("Data Source=shop.db", sqlite => sqlite.CommandTimeout(30)); ```
  • Limited ALTER TABLE: many schema changes require rebuilding the table. EF's migrations do this automatically, but review them on large tables.
  • Type affinity: SQLite has few native types. decimal, DateTimeOffset and TimeSpan are stored as text or integers, so some operations on them can't be translated. EF 10 added MIN/MAX/ORDER BY support for decimal on SQLite. Check the provider's limitations page for your version, and plan value converters if you query on these types heavily.
  • Concurrency: one writer at a time. WAL journal mode (PRAGMA journal_mode=WAL;) lets readers proceed during writes. Check the current mode with PRAGMA journal_mode;.
  • In-memory databases (Data Source=:memory:) live only as long as their connection stays open. That matters for tests (Lesson 9).

Supporting several providers

If the same model must run on more than one database (for example SQL Server in production and SQLite for a desktop edition):

  • Generate separate migration sets per provider, each in its own assembly (MigrationsAssembly), because migrations contain provider-specific SQL and types.
  • Keep provider-specific model configuration behind Database.IsSqlServer() / IsNpgsql() checks in OnModelCreating.
  • Test against every provider you ship. Translation differences are real.

🔑 Key takeaways

  • Provider options (UseSqlServer(conn, sql => …)) change the generated SQL and runtime behaviour. Configure them deliberately.
  • Match UseCompatibilityLevel / SetPostgresVersion to your real server. EF 10 uses the json type at level 170+ or with UseAzureSql.
  • PostgreSQL: store UTC DateTime for timestamptz. Consider snake_case naming and native enums.
  • SQLite has type and ALTER TABLE limitations. Multi-provider apps need one migration set per provider.

Exercise

🛠 Provider tune-up

  1. Run SELECT compatibility_level FROM sys.databases WHERE name = DB_NAME() and set UseCompatibilityLevel to match.
  2. Set UseCompatibilityLevel(120) and run db.Orders.Where(o => ids.Contains(o.Id)) with a parameterized collection mode. Compare the SQL with level 160. What changed and why?
  3. If you have PostgreSQL, insert an order with DateTime.Now into a timestamptz column and read the exception. Fix it with DateTime.UtcNow.
What you should see

At compatibility level 120, EF can't use OPENJSON, so translations that rely on it fall back to other forms, such as inlined values. With Npgsql, writing a Local DateTime to timestamptz throws an exception explaining that only UTC is supported.
