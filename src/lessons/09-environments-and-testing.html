Environments, Testing & Configuration Safety

Development, CI, staging and production each need different EF settings, and you need proof that each configuration works. This lesson covers environment-specific configuration, startup validation, health checks and testing strategies.

⏱ 35 min
🎯 Goal of this lesson

Learn to vary EF configuration safely across environments and to verify it automatically: debug features on where they help, off where they hurt, misconfiguration caught before traffic arrives, and tests that exercise the real database behaviour.

Why it matters: "worked in dev, broke in prod" usually means the environments were configured differently in ways nobody tested. Sensitive-data logging left on leaks personal data. Tests on the wrong provider pass while production fails. These are configuration mistakes you can prevent systematically.

By the end of this lesson you will be able to

  • Layer configuration by environment, and know which EF settings belong where.
  • Validate configuration at startup and expose database health checks.
  • Choose a testing strategy: real database in a container, SQLite in-memory, or fakes.
  • Replace the DbContext configuration in integration tests with WebApplicationFactory.

Environment layering

ASP.NET Core loads configuration in layers. Later sources override earlier ones:

  1. appsettings.json: shared defaults, no secrets.
  2. appsettings.{Environment}.json: per-environment overrides (Development, Staging, Production).
  3. User secrets (Development only).
  4. Environment variables.
  5. Command-line arguments.

Fail fast: validation and health checks

Validate settings at startup (Lesson 5's ValidateOnStart), and give the platform a way to ask "can this instance reach its database?":

```csharp // Package: Microsoft.Extensions.Diagnostics.HealthChecks.EntityFrameworkCore builder.Services.AddHealthChecks() .AddDbContextCheck("database", tags: ["ready"]); app.MapHealthChecks("/health/ready", new HealthCheckOptions { Predicate = c => c.Tags.Contains("ready") }); app.MapHealthChecks("/health/live", new HealthCheckOptions { Predicate = _ => false }); // process is up ```

Point the Kubernetes readiness probe, or the load balancer health check, at /health/ready. That way instances with broken configuration never receive traffic, and liveness doesn't restart pods just because the database had a blip.

EF InMemory provider❌ Not relational: no SQL, no constraints, no transactions, different query semanticsVery fastThe EF team discourages it for testing. Avoid it.

Integration tests with Testcontainers

```csharp // Packages: Testcontainers.MsSql, Microsoft.AspNetCore.Mvc.Testing, xunit public sealed class ApiFactory : WebApplicationFactory, IAsyncLifetime { private readonly MsSqlContainer _db = new MsSqlBuilder().Build(); protected override void ConfigureWebHost(IWebHostBuilder builder) { builder.UseEnvironment("Testing"); builder.ConfigureTestServices(services => { // Remove the app's registration, then add one pointing at the container services.RemoveAll>(); services.RemoveAll>(); // EF 9+ registration services.AddDbContext(o => o.UseSqlServer(_db.GetConnectionString())); }); } public async Task InitializeAsync() { await _db.StartAsync(); using var scope = Services.CreateScope(); await scope.ServiceProvider.GetRequiredService().Database.MigrateAsync(); } public new async Task DisposeAsync() => await _db.DisposeAsync(); } ```

SQLite in-memory: keep the connection open

```csharp var connection = new SqliteConnection("Data Source=:memory:"); connection.Open(); // the database lives as long as this connection var options = new DbContextOptionsBuilder().UseSqlite(connection).Options; using (var ctx = new ShopContext(options)) ctx.Database.EnsureCreated(); // ... run tests with new ShopContext(options) ... connection.Dispose(); // database disappears ```
Test the configuration itself Add a cheap test that builds the real host with production-like settings (minus secrets) and resolves ShopContext. Then assert on db.Model or db.Database.ProviderName. It catches broken DI registrations, invalid options and model validation errors on every build.
