Tracking vs No-Tracking Queries

By default, every entity EF Core loads is registered in the change tracker and snapshotted. That's essential when you plan to update entities, and pure overhead when you only read them. This lesson shows how to choose.

⏱ 25 min
🎯 Goal of this lesson

Learn when change tracking is needed and when it's pure overhead, and how to read and update data without paying for tracking you don't use.

Why it matters: Tracking costs CPU and memory on every row. Choosing the right tracking mode is often the cheapest speed-up for read-heavy endpoints, and understanding it prevents subtle update bugs.

By the end of this lesson you will be able to

  • Explain what tracking costs: memory, snapshots, identity resolution and DetectChanges.
  • Use AsNoTracking, AsNoTrackingWithIdentityResolution and AsTracking.
  • Set a context-wide default tracking behaviour.
  • Update entities without loading them, using Attach and Entry.

What tracking does

For each entity returned by a tracking query, EF:

  1. Looks up its key in the identity map. If an instance with that key is already tracked, EF returns that same instance and throws away the new row data. This is identity resolution.
  2. Otherwise it creates an InternalEntityEntry, stores a snapshot of original values, and fixes up navigation properties to other tracked entities.
  3. Later, SaveChanges() (and many other APIs) call DetectChanges(), which compares every tracked entity with its snapshot.

None of this is needed for read-only scenarios such as API GET endpoints, reports, exports and view models.

AsNoTracking

```csharp var products = await db.Products .AsNoTracking() .Where(p => p.CategoryId == categoryId) .ToListAsync(); ```

The SQL is identical. Only the work EF does in .NET changes. Microsoft's benchmarks and many community measurements show no-tracking queries are noticeably faster and allocate much less memory. The gap grows with the number of rows returned.

The catch: no identity resolution Without tracking, the same database row returned twice becomes two separate objects. Loading 1,000 orders with Include(o => o.Customer) where all orders belong to 3 customers gives you 1,000 Customer instances, not 3.

AsNoTrackingWithIdentityResolution

This gives you de-duplicated instances without full tracking. EF uses a temporary identity map for the duration of the query, then discards it:

```csharp var orders = await db.Orders .AsNoTrackingWithIdentityResolution() .Include(o => o.Customer) .ToListAsync(); // orders sharing a customer point to the SAME Customer object ```

It's slower than plain AsNoTracking but faster than tracking. Use it when you serialize graphs with shared references or need reference equality.

Choosing a tracking mode

ScenarioUse
Load, modify, SaveChangesTracking (the default)
Read-only list or detail returned as JSONAsNoTracking(), or better, a projection (Lesson 11)
Read-only graph with many shared referencesAsNoTrackingWithIdentityResolution()
Projection to a DTO or anonymous typeNothing needed. Non-entity results aren't tracked.
Projections are untracked automatically db.Products.Select(p => new ProductDto(p.Id, p.Name)) is never tracked, because DTOs aren't entities. If a projection contains an entity instance, such as new { Product = p, p.Category.Name }, that entity is tracked in a tracking query.

Context-wide default

For read-heavy services, make no-tracking the default and opt in where you write:

```csharp builder.Services.AddDbContext(o => o .UseSqlServer(connStr) .UseQueryTrackingBehavior(QueryTrackingBehavior.NoTracking)); // When you need to update: var order = await db.Orders.AsTracking().SingleAsync(o => o.Id == id); order.Status = OrderStatus.Shipped; await db.SaveChangesAsync(); ```

You can also change it per context instance: db.ChangeTracker.QueryTrackingBehavior = QueryTrackingBehavior.NoTracking;.

Read/write separation A common pattern in larger systems is a ReadShopContext with no-tracking defaults, possibly pointed at a read replica, alongside the normal writable context. Query handlers inject the read context and command handlers the write context.

Updating without loading

If you already know the key and the new values, you don't need a SELECT first:

```csharp // Update one column of a known row: 1 round trip instead of 2 var product = new Product { Id = productId }; db.Products.Attach(product); // tracked as Unchanged product.Price = newPrice; // only Price becomes Modified await db.SaveChangesAsync(); // UPDATE [Products] SET [Price] = @p0 WHERE [Id] = @p1 ```

For set-based updates of many rows there's an even better tool, ExecuteUpdateAsync (Lesson 16).

Careful with Update() db.Update(entity) marks every property as modified and updates all columns, including ones you didn't change, and it walks the whole reachable graph. Prefer Attach plus setting the changed properties, or Entry(e).Property(x => x.Price).IsModified = true.

Keeping the change tracker small

Long-lived contexts with thousands of tracked entities make every DetectChanges slower. When processing in batches:

```csharp foreach (var batch in ids.Chunk(1000)) { var items = await db.Orders.Where(o => batch.Contains(o.Id)).ToListAsync(); foreach (var o in items) o.Status = OrderStatus.Shipped; await db.SaveChangesAsync(); db.ChangeTracker.Clear(); // forget everything tracked so far } ```

Exercise

🛠 Measure it

  1. Load all 10,000 orders with Include(o => o.Customer) three ways: tracking, AsNoTracking, AsNoTrackingWithIdentityResolution.
  2. Time each with Stopwatch (run each a few times and discard the first) and check memory with GC.GetAllocatedBytesForCurrentThread().
  3. Count distinct customer instances: orders.Select(o => o.Customer).Distinct(ReferenceEqualityComparer.Instance).Count().
What to expect

No-tracking is fastest and allocates least, but you get about 10,000 Customer instances. Both other modes give about 1,000. In Lesson 25 you'll redo this properly with BenchmarkDotNet.
