Indexes & Migrations

Perfect LINQ on top of a missing index is still slow. This lesson covers defining indexes in your EF model, designing them for your queries, and shipping schema changes safely.

⏱ 35 min
🎯 Goal of this lesson

Learn to design indexes from your queries, define them in the EF model, and deploy schema changes safely.

Why it matters: Perfect LINQ on top of a missing index is still a full table scan. Indexes are usually the largest single lever on query speed, and migrations are how they reach production safely.

By the end of this lesson you will be able to

  • Define unique, composite, filtered, descending and covering indexes with the Fluent API.
  • Design indexes from your actual query patterns.
  • Recognize LINQ patterns that prevent index use.
  • Deploy migrations safely with SQL scripts and migration bundles.

Indexes in the EF model

EF creates indexes for primary keys and foreign keys by convention. Every other index comes from you:

```csharp modelBuilder.Entity(b => { // Unique index b.HasIndex(c => c.Email).IsUnique(); // Named index b.HasIndex(c => c.CreatedUtc).HasDatabaseName("IX_Customers_Created"); }); modelBuilder.Entity(b => { // Composite index: column order matters! b.HasIndex(o => new { o.CustomerId, o.PlacedUtc }); // Filtered (partial) index: only "open" orders b.HasIndex(o => o.PlacedUtc) .HasFilter("[Status] = 0") // SQL Server syntax; PostgreSQL: "\"Status\" = 0" .HasDatabaseName("IX_Orders_Pending_Placed"); // Descending index (EF Core 7+) b.HasIndex(o => new { o.PlacedUtc, o.Id }).IsDescending(true, true); }); modelBuilder.Entity(b => { // Covering index: SQL Server INCLUDE columns b.HasIndex(p => p.CategoryId) .IncludeProperties(p => new { p.Name, p.Price }); }); ```

Designing indexes from queries

Index design starts from the queries, not the tables. For each important query, look at its WHERE, JOIN, ORDER BY and SELECT columns.

Composite index column order

An index on (CustomerId, PlacedUtc) is like a phone book sorted by last name, then first name. It efficiently supports:

  • WHERE CustomerId = @x ✅
  • WHERE CustomerId = @x ORDER BY PlacedUtc DESC ✅ (no sort needed)
  • WHERE CustomerId = @x AND PlacedUtc > @d ✅
  • WHERE PlacedUtc > @d ❌ (can't seek on the second column alone)

Rule of thumb: equality columns first, then range or sort columns.

Covering indexes and projections

When an index contains every column a query needs, the database never touches the base table, so there are no key lookups. That's why projections (Lesson 11) and covering indexes work so well together:

```csharp // Served entirely by IX_Products_CategoryId INCLUDE (Name, Price) db.Products.Where(p => p.CategoryId == id).Select(p => new { p.Id, p.Name, p.Price }); ```

Let the database tell you SQL Server's missing-index DMVs (sys.dm_db_missing_index_details), Query Store, and PostgreSQL's pg_stat_statements plus EXPLAIN ANALYZE show which indexes your workload actually needs. Treat their suggestions as hints and avoid duplicate or overlapping indexes. Every index makes inserts and updates slower.

Migrations

```bash dotnet ef migrations add AddOrderIndexes dotnet ef migrations list dotnet ef migrations remove # undo last (if not applied) ```

Always review the generated migration. Look for unintended table rebuilds, column drops caused by renames (EF may see a rename as drop plus add), and data-type changes on large tables.

Deploying migrations safely

ApproachHowProduction?
context.Database.Migrate() at startupThe app migrates itself on boot⚠ Not recommended for production: the app needs DDL permissions, startup gets slower, and a failed migration takes the app down. EF 9+ takes a lock so instances don't migrate concurrently, but the other risks remain. OK for dev and simple apps.
Idempotent SQL scriptdotnet ef migrations script --idempotent -o migrate.sql✅ Reviewable by a DBA and runnable from CI/CD
Migration bundledotnet ef migrations bundle --self-contained -r linux-x64 → ./efbundle --connection "..."✅ A single executable, ideal for pipelines

Large-table operations

Creating an index on a 100M-row table can lock it. On SQL Server Enterprise or Azure SQL, use online index builds:

```csharp b.HasIndex(o => o.PlacedUtc).IsCreatedOnline(); // SQL Server: WITH (ONLINE = ON) ```

For risky changes, use custom SQL in the migration with migrationBuilder.Sql(...), and split schema changes into expand and contract phases: add a column, backfill it, switch the code over, then drop the old column.

Exercise

🛠 Index for your queries

Design the indexes for these three queries, add them to the model, and generate a migration:

  1. A customer's orders, newest first: Where(o => o.CustomerId == id).OrderByDescending(o => o.PlacedUtc)
  2. The pending orders queue, oldest first: Where(o => o.Status == OrderStatus.Pending).OrderBy(o => o.PlacedUtc)
  3. A product search by SKU prefix that projects Id, Name and Price.
Show solution ```csharp modelBuilder.Entity(b => { b.HasIndex(o => new { o.CustomerId, o.PlacedUtc }).IsDescending(false, true); b.HasIndex(o => o.PlacedUtc).HasFilter("[Status] = 0").HasDatabaseName("IX_Orders_PendingQueue"); }); modelBuilder.Entity() .HasIndex(p => p.Sku).IsUnique().IncludeProperties(p => new { p.Name, p.Price }); // and use p.Sku.StartsWith(prefix) → LIKE 'prefix%' (index seek) ```

Note: the FK convention originally created an index on CustomerId alone. When you add a composite index that starts with CustomerId, EF sees that the FK is already covered and stops creating the separate index. Your migration will drop IX_Orders_CustomerId, which means one less index to maintain on every write.
