Concurrency, Transactions & Resiliency

Fast code that loses updates or falls over on a transient network blip isn't production-ready. This lesson covers optimistic concurrency, transaction scope and isolation, and connection resiliency, all with performance in mind.

⏱ 35 min
🎯 Goal of this lesson

Learn to keep data correct under concurrency and failures without sacrificing throughput: optimistic concurrency, short transactions and connection resiliency.

Why it matters: Fast code that loses updates or crashes on a transient network error isn't production-ready. These patterns protect data integrity while avoiding costly locks.

By the end of this lesson you will be able to

  • Resolve DbUpdateConcurrencyException correctly.
  • Use explicit transactions, and keep them short.
  • Configure retry-on-failure and combine it correctly with user transactions.

Optimistic concurrency

Pessimistic locking (holding locks while a user edits) kills throughput. EF uses optimistic concurrency: it assumes conflicts are rare, includes a version check in the UPDATE, and throws if someone else changed the row first.

```csharp public class Product { // ... [Timestamp] // SQL Server rowversion public byte[] RowVersion { get; set; } = null!; } // or Fluent API modelBuilder.Entity().Property(p => p.RowVersion).IsRowVersion(); ``` ```sql label="Generated UPDATE" UPDATE [Products] SET [Price] = @p0 OUTPUT INSERTED.[RowVersion] WHERE [Id] = @p1 AND [RowVersion] = @p2; ```

If zero rows are affected, EF throws DbUpdateConcurrencyException.

Other providers
  • PostgreSQL: map the system column xmin: b.Property<uint>("Version").IsRowVersion(); (Npgsql 7+).
  • SQLite and others: use a regular column as a concurrency token, .IsConcurrencyToken(), and update it yourself (e.g. a Guid Version you regenerate on each save).

Handling conflicts

```csharp const int maxAttempts = 3; for (var attempt = 1; ; attempt++) { try { await db.SaveChangesAsync(); break; } catch (DbUpdateConcurrencyException ex) when (attempt < maxAttempts) // don't retry forever { foreach (var entry in ex.Entries) { var dbValues = await entry.GetDatabaseValuesAsync(); if (dbValues is null) throw; // row was deleted // Strategy A, "client wins": refresh the original values, keep ours entry.OriginalValues.SetValues(dbValues); // Strategy B, "database wins": entry.CurrentValues.SetValues(dbValues); // Strategy C: merge property-by-property, or return 409 Conflict to the user } } } ```

In web APIs, the usual pattern is to send the RowVersion to the client and back with the edit, set it as the original value, and return 409 Conflict when it fails:

```csharp var product = await db.Products.SingleAsync(p => p.Id == dto.Id); db.Entry(product).Property(p => p.RowVersion).OriginalValue = dto.RowVersion; product.Price = dto.Price; try { await db.SaveChangesAsync(); } catch (DbUpdateConcurrencyException) { return Results.Conflict(); } ```

Transactions

Each SaveChanges call is already atomic. Use an explicit transaction only when several operations must succeed or fail together: multiple SaveChanges calls, ExecuteUpdate combined with SaveChanges, or raw SQL.

```csharp await using var tx = await db.Database.BeginTransactionAsync(); await db.Orders.Where(o => o.Id == orderId) .ExecuteUpdateAsync(s => s.SetProperty(o => o.Status, OrderStatus.Paid)); db.Payments.Add(new Payment { OrderId = orderId, Amount = amount }); await db.SaveChangesAsync(); await tx.CommitAsync(); // disposing without commit = rollback ```
Keep transactions short Locks are held until commit. Never await HTTP calls, message brokers or user input inside a transaction. Do the slow work first, then open the transaction, write and commit. Long transactions are a top cause of blocking and deadlocks.

Isolation levels and blocking

The default isolation level on SQL Server is READ COMMITTED, where readers can block writers and vice versa. Many high-throughput SQL Server systems enable Read Committed Snapshot Isolation (RCSI) at the database level. Readers then see the last committed version without taking shared locks, which removes most reader/writer blocking. It's the default on Azure SQL Database.

```sql ALTER DATABASE Shop SET READ_COMMITTED_SNAPSHOT ON; ```

Request a specific isolation level per transaction if you need one: BeginTransactionAsync(IsolationLevel.Serializable). PostgreSQL uses MVCC, so readers never block writers by default.

Connection resiliency

Cloud databases have transient failures: failovers, throttling, dropped connections. EF's execution strategies retry automatically:

```csharp options.UseSqlServer(connStr, sql => sql.EnableRetryOnFailure( maxRetryCount: 5, maxRetryDelay: TimeSpan.FromSeconds(10), errorNumbersToAdd: null)); // PostgreSQL: options.UseNpgsql(connStr, o => o.EnableRetryOnFailure()); ```
Retries + your own transaction = exception With a retrying strategy, EF can't retry a block of operations you started yourself. It doesn't know where the unit begins. BeginTransaction throws "The configured execution strategy does not support user-initiated transactions". Wrap the whole unit in the strategy:
```csharp var strategy = db.Database.CreateExecutionStrategy(); await strategy.ExecuteAsync(async () => { await using var tx = await db.Database.BeginTransactionAsync(); // ... all operations of the unit ... await db.SaveChangesAsync(); await tx.CommitAsync(); }); ```

The delegate may run more than once, so make it idempotent. Don't, for example, add entities to the context outside the delegate and then retry. Create or attach them inside it.

  2. Add [Timestamp] RowVersion, migrate, and repeat. Catch the exception and implement "database wins".
  3. Enable EnableRetryOnFailure and try BeginTransactionAsync directly. Read the exception, then fix it with CreateExecutionStrategy.
