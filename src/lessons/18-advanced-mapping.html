Advanced Mapping for Performance

Mapping decisions are performance decisions. Inheritance strategy, value objects, JSON columns, table splitting and value converters all change the SQL EF generates. This lesson covers the trade-offs.

⏱ 40 min

By the end of this lesson you will be able to

  • Choose between TPH, TPT and TPC inheritance based on query patterns.
  • Use complex types, owned types and JSON columns appropriately.
  • Use table splitting to avoid loading large columns.
  • Understand the query impact of value converters and primitive collections.

Inheritance mapping strategies

Suppose a Payment base class has subclasses CardPayment, BankTransfer and WalletPayment.

```csharp // TPH: default, one table with a discriminator column modelBuilder.Entity().HasDiscriminator("Kind"); // TPT: one table per type, joined on the primary key modelBuilder.Entity().UseTptMappingStrategy(); // TPC: one table per CONCRETE type, no shared base table (EF Core 7+) modelBuilder.Entity().UseTpcMappingStrategy(); ```
TPH (table-per-hierarchy)TPT (table-per-type)TPC (table-per-concrete-type)
Query all payments✅ Single table scan❌ LEFT JOINs to every subtype table⚠ UNION ALL across tables
Query one subtype✅ WHERE Kind = 'Card'⚠ JOIN base + subtype✅ Single table, no JOIN
Insert✅ 1 row❌ 2+ rows in 2+ tables✅ 1 row
SchemaMany nullable columnsNormalizedColumns duplicated per table
KeysIdentity OKIdentity OKNeeds keys unique across tables (EF uses a sequence by default)
Guidance from the EF team Use TPH by default: it's generally the fastest. Use TPC when you mostly query individual leaf types and the hierarchy is wide. Avoid TPT unless an existing schema forces it, because its JOINs grow with the hierarchy.

Value objects: complex types vs owned types

For a value like Address (Street, City, Zip) stored in the owner's table:

```csharp public record Address(string Street, string City, string Zip); // Complex type (EF Core 8+): value semantics, no identity, columns in the owner's table modelBuilder.Entity().ComplexProperty(c => c.ShippingAddress); // Owned type: has a hidden key, tracked like an entity modelBuilder.Entity().OwnsOne(c => c.BillingAddress); ```
  • Complex types are the modern choice for value objects. They're compared by value, you can assign the same instance to two properties, and they carry no identity overhead. EF 10 added optional (nullable) complex types and JSON mapping for them.
  • Owned types behave more like dependent entities with keys. Use them where you need identity semantics, or for owned collections on older EF versions.

JSON columns

Store a nested structure in one JSON column instead of extra tables and joins:

```csharp public class Order { // ... public ShippingInfo Shipping { get; set; } = null!; } public class ShippingInfo { public string Carrier { get; set; } = ""; public string TrackingNo { get; set; } = ""; public List Events { get; set; } = new(); } // EF 10: complex type mapped to JSON modelBuilder.Entity().ComplexProperty(o => o.Shipping, s => s.ToJson()); // EF 7–9: modelBuilder.Entity().OwnsOne(o => o.Shipping, s => s.ToJson()); // LINQ queries into the JSON document var fedex = await db.Orders.Where(o => o.Shipping.Carrier == "FedEx").ToListAsync(); // SQL Server: WHERE JSON_VALUE([o].[Shipping], '$.Carrier') = N'FedEx' ```

Good for: data always read and written together with its owner, flexible attributes, event lists. It saves joins and tables.

Watch out: predicates on JSON properties can't use a normal index. On SQL Server, add a computed column over JSON_VALUE and index it. On PostgreSQL, use jsonb with a GIN or expression index. Large documents are rewritten on update. Newer SQL Server and Azure SQL versions have a native json type that EF 10 can target.

Table splitting: lazy columns without lazy loading

Most product queries never need the 2 KB Description. Projections are one answer (Lesson 6). Table splitting is another: map two entity types to the same table, and load the heavy part only when needed.

```csharp public class Product { public int Id { get; set; } public string Name { get; set; } = ""; public decimal Price { get; set; } public ProductDetails Details { get; set; } = null!; } public class ProductDetails { public int Id { get; set; } public string Description { get; set; } = ""; public byte[]? Image { get; set; } } modelBuilder.Entity(b => { b.ToTable("Products"); b.HasOne(p => p.Details).WithOne().HasForeignKey(d => d.Id); }); modelBuilder.Entity().ToTable("Products"); var list = await db.Products.ToListAsync(); // no Description/Image var full = await db.Products.Include(p => p.Details).SingleAsync(p => p.Id == id); ```

Value converters

```csharp modelBuilder.Entity().Property(o => o.Status).HasConversion().HasMaxLength(16); ```
  • Comparisons and equality on converted properties work. EF converts the parameter, not the column, so indexes are still used.
  • ⚠ Ordering uses the stored representation: enum-as-string sorts alphabetically, not by enum value.
  • ⚠ Operations that depend on the .NET type's semantics, such as range comparisons on a value encrypted or serialized by a converter, can't translate meaningfully.
  • Converters add a small per-value materialization cost. Usually negligible.

Primitive collections

EF Core 8+ maps List<string>, int[] and similar to a JSON column automatically:

```csharp public class Product { /* ... */ public List Tags { get; set; } = new(); } var tagged = await db.Products.Where(p => p.Tags.Contains("sale")).ToListAsync(); // SQL Server: WHERE N'sale' IN (SELECT [t].[value] FROM OPENJSON([p].[Tags]) AS [t]) ```

It's convenient, but every such filter shreds the JSON for each row, so it can't use an index. If you filter by tags frequently and the table is large, model a proper ProductTag table with an index. On PostgreSQL, native arrays with a GIN index are an efficient alternative.
