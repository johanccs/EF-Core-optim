Diagnosing Performance Problems

Optimization without measurement is guesswork. This lesson builds a diagnostic toolkit, from logs and query tags to execution plans, EF metrics and distributed tracing, so you can find the slow query before your users do.

⏱ 35 min
🎯 Goal of this lesson

Build a repeatable diagnostic workflow: find slow or chatty queries, trace them back to code, and explain them with execution plans and metrics.

Why it matters: Optimization without measurement is guesswork. These tools turn "the app is slow" into a specific query, a specific cause and a verifiable fix.

By the end of this lesson you will be able to

  • Follow a repeatable workflow: measure, locate, explain, fix, verify.
  • Tag queries so you can trace SQL back to C# code.
  • Read execution plans and spot the usual culprits.
  • Monitor EF Core with dotnet-counters and OpenTelemetry.

The workflow

  1. Measure. Which endpoint or job is slow? Use APM, traces and logs, not intuition.
  2. Locate. Which SQL statements does it run, how many, and how long does each take?
  3. Explain. Why is that statement slow? Look at the execution plan, rows read, waits and blocking.
  4. Fix. Apply the technique from the earlier lessons: fewer round trips, less data, an index, a better query shape.
  5. Verify. Measure again, ideally with a benchmark or load test (Lesson 25).

1. Command logging with durations

Every executed command log includes its duration: Executed DbCommand (1,284ms). In production, keep this category at Warning and log slow commands only, using an interceptor:

```csharp public sealed class SlowQueryInterceptor(ILogger logger) : DbCommandInterceptor { private static readonly TimeSpan Threshold = TimeSpan.FromMilliseconds(500); public override ValueTask ReaderExecutedAsync( DbCommand command, CommandExecutedEventData eventData, DbDataReader result, CancellationToken ct = default) { if (eventData.Duration > Threshold) logger.LogWarning("Slow query ({Ms} ms): {Sql}", eventData.Duration.TotalMilliseconds, command.CommandText); return ValueTask.FromResult(result); } // Also override ReaderExecuted (sync), NonQueryExecuted(Async) and ScalarExecuted(Async) // if you want SaveChanges, ExecuteUpdate and sync queries covered too. } builder.Services.AddSingleton(); builder.Services.AddDbContext((sp, o) => o .UseSqlServer(connStr) .AddInterceptors(sp.GetRequiredService())); ```

2. Query tags: from SQL back to code

When a DBA sends you a slow SQL statement, which C# line produced it? Tag your queries:

```csharp var orders = await db.Orders .TagWith("OrdersController.GetRecent: dashboard list") .Where(o => o.CustomerId == id) .ToListAsync(); // EF Core 7+: adds file name and line number automatically var q = db.Orders.TagWithCallSite().Where(o => o.Status == OrderStatus.Pending); ``` ```sql -- OrdersController.GetRecent: dashboard list SELECT [o].[Id], ... FROM [Orders] AS [o] WHERE [o].[CustomerId] = @id ```

Tags appear in Query Store, Extended Events, pg_stat_statements and your APM tool.

3. Execution plans

Copy the SQL (from logs or ToQueryString()), run it in SSMS or Azure Data Studio with Include Actual Execution Plan (or EXPLAIN (ANALYZE, BUFFERS) in PostgreSQL), and look for:

Plan smellLikely causeFix
Table/Clustered Index Scan on a big tableMissing index, or a non-sargable predicateLesson 14: index or rewrite the filter
Key Lookup executed thousands of timesIndex doesn't cover the selected columnsProject fewer columns, or add INCLUDE columns
Estimated rows ≪ actual rowsStale statistics, parameter sniffingUpdate statistics. See parameter sniffing below.
Expensive Sort with a spill warningORDER BY without a supporting index, or too small a memory grantAn index matching the ORDER BY
CONVERT_IMPLICIT warningParameter type doesn't match the columnFix the model's column type or unicode setting
Parameter sniffing SQL Server compiles a plan for the first parameter values it sees and reuses it. That's great for most queries, but bad when data is skewed. A plan built for a customer with 3 orders may be terrible for one with 3 million. Mitigations: Query Store plan forcing, OPTION (RECOMPILE) through an interceptor or raw SQL on specific queries, and SQL Server 2022's Parameter Sensitive Plan optimization.

4. Database-side tools

  • SQL Server Query Store: top resource-consuming queries over time, plan regressions, forced plans. Enable it on every production database.
  • DMVs: sys.dm_exec_query_stats, sys.dm_db_missing_index_details, sys.dm_os_wait_stats.
  • PostgreSQL: pg_stat_statements, auto_explain, EXPLAIN ANALYZE.

5. EF Core metrics

EF Core publishes runtime metrics under the meter or event source name Microsoft.EntityFrameworkCore. EF Core 9+ uses System.Diagnostics.Metrics, and earlier versions use EventCounters. Watch a running process:

```bash dotnet tool install --global dotnet-counters dotnet-counters monitor --counters Microsoft.EntityFrameworkCore -p ```

EF 9+ instruments include microsoft.entityframeworkcore.active_dbcontexts, .queries, .savechanges, .compiled_query_cache_hits / .compiled_query_cache_misses, .optimistic_concurrency_failures and .execution_strategy_operation_failures. The most telling signal is the query cache hit ratio, hits ÷ (hits + misses). After warm-up it should stay close to 100% (see Lesson 21). The legacy event counters show it directly as "Query Cache Hit Rate (%)". A steadily growing active DbContexts count suggests contexts aren't being disposed.

6. Distributed tracing with OpenTelemetry

Traces show each request with its database calls as child spans, which makes N+1 queries and slow statements obvious.

```csharp builder.Services.AddOpenTelemetry() .WithTracing(t => t .AddAspNetCoreInstrumentation() .AddSqlClientInstrumentation() // or .AddEntityFrameworkCoreInstrumentation() .AddOtlpExporter()) .WithMetrics(m => m .AddAspNetCoreInstrumentation() .AddMeter("Microsoft.EntityFrameworkCore") .AddOtlpExporter()); ```

Send the data to .NET Aspire's dashboard locally, or to Jaeger, Grafana, Azure Monitor, Datadog or Honeycomb in production.

Exercise

🛠 Build your toolkit

  1. Add SlowQueryInterceptor with a 50 ms threshold to the playground, and run a deliberately bad query (e.g. Name.Contains on 1M rows).
  2. Tag three queries with TagWithCallSite() and find them in the log output.
  3. Capture the actual execution plan for the slow query. Fix it, then capture the plan again.
  4. Run dotnet-counters monitor while hitting an endpoint in a loop, and compare the query cache hits with misses.
