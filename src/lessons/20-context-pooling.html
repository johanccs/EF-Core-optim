DbContext Pooling & Factories

At thousands of requests per second, even creating and wiring up a DbContext shows up in profiles. DbContext pooling reuses context instances. This lesson covers how pooling works, what it costs, and the state-related bugs to avoid.

⏱ 25 min
🎯 Goal of this lesson

Understand DbContext pooling: what it saves, how to enable it, and how to avoid the state-leak bugs it can introduce.

Why it matters: At high throughput, context setup becomes measurable overhead. Pooling removes it, but only if you understand what is and isn't reset between requests.

By the end of this lesson you will be able to

  • Enable pooling with AddDbContextPool and AddPooledDbContextFactory.
  • Explain what is and isn't reset when a context returns to the pool.
  • Pass per-request state, such as a tenant id, into pooled contexts safely.
  • Decide whether pooling is worth it for your workload.

What pooling does

Without pooling, each request creates a new DbContext, which allocates its internal service graph, change tracker and state manager, then throws it away. With pooling, EF keeps a pool of already-initialized instances. When your code disposes a context, EF resets its state and returns it to the pool for the next request.

```csharp builder.Services.AddDbContextPool( o => o.UseSqlServer(connStr), poolSize: 1024); // max instances retained (default 1024) ```

Consumers don't change. They still inject ShopContext per request.

Pooled factories

For Blazor, background services or any code that creates contexts on demand:

```csharp builder.Services.AddPooledDbContextFactory(o => o.UseSqlServer(connStr)); public class ImportService(IDbContextFactory factory) { public async Task RunAsync() { await using var db = await factory.CreateDbContextAsync(); // rented from the pool // ... } // returned to the pool } ```

Outside dependency injection, for example in benchmarks or console tools:

```csharp var options = new DbContextOptionsBuilder().UseSqlServer(connStr).Options; var factory = new PooledDbContextFactory(options); await using var db = factory.CreateDbContext(); ```

Requirements and pitfalls

  • Options are fixed. The options delegate runs once, not per request, so you can't configure a different connection string per request inside it. OnConfiguring also isn't the place for per-request settings.
  • Constructor. The context needs a public constructor accepting DbContextOptions<TContext>. Don't inject scoped services into a pooled context's constructor. It would capture the first request's instance forever.
  • Your own fields aren't reset. EF resets the change tracker and its own state. Any field you add, such as public int TenantId or a cached list, carries over to the next request that rents the instance.
The cross-tenant data leak A pooled context with a TenantId field set in one request and not reset in the next could serve tenant A's data to tenant B. Always set the state on every rent, as in the pattern below. Never rely on a value set in an earlier request.

Per-request state with pooling

The pattern from the official docs: register a pooled factory, then a scoped wrapper that sets state each time it creates a context:

```csharp public class ShopContext(DbContextOptions options) : DbContext(options) { public int TenantId { get; set; } protected override void OnModelCreating(ModelBuilder b) { b.Entity().HasQueryFilter(o => o.TenantId == TenantId); // evaluated per query } } public class TenantContextFactory(IDbContextFactory pooled, ITenantProvider tenant) : IDbContextFactory { public ShopContext CreateDbContext() { var ctx = pooled.CreateDbContext(); ctx.TenantId = tenant.CurrentTenantId; // set on EVERY rent return ctx; } } // Registration builder.Services.AddPooledDbContextFactory(o => o.UseSqlServer(connStr)); builder.Services.AddScoped(); builder.Services.AddScoped(sp => sp.GetRequiredService().CreateDbContext()); ```

Is it worth it?

Pooling saves a fixed amount of CPU and allocation per context instance, typically microseconds. It makes a measurable difference only when context creation is a meaningful share of the request:

  • ✅ High-throughput APIs with simple, fast queries (cache-like reads, thousands of requests per second).
  • ✅ Services where profiles show context initialization or GC pressure from contexts.
  • ➖ Typical line-of-business apps with 10–100 ms queries, where the gain disappears in the noise.

Pooling has low risk as long as your context holds no custom state, so many teams enable it by default. Measure it with the BenchmarkDotNet approach from Lesson 25.

Reminder: two different pools DbContext pooling reuses .NET objects. ADO.NET connection pooling reuses database connections, which is the bigger win, and it's already on. A pooled context still opens and closes connections per operation through the connection pool.
