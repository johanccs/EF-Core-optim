Interceptors, Query Filters & Conventions

Cross-cutting concerns such as soft delete, multi-tenancy, auditing, query hints and monitoring belong in one place, not copied into every query. This lesson covers EF's extension points and how to use them without adding overhead.

⏱ 35 min
🎯 Goal of this lesson

Learn to implement cross-cutting concerns once (auditing, soft delete, multi-tenancy, query hints, monitoring) using interceptors, query filters and conventions.

Why it matters: Copy-pasted cross-cutting logic drifts and causes bugs and data leaks. Centralized extension points keep it consistent, but they run on every operation, so they must stay cheap.

By the end of this lesson you will be able to

  • Write command, SaveChanges and materialization interceptors.
  • Use global query filters for soft delete and tenancy, including EF 10 named filters.
  • Index for query filters so they stay fast.
  • Write a custom model-building convention.

Interceptors

Interceptors let you observe and modify EF operations. The main kinds:

Interface / base classInterceptsTypical use
DbCommandInterceptorCommand creation and executionSlow-query logging, query hints, command counting
DbConnectionInterceptorOpening and closing connectionsSetting session context (e.g. SESSION_CONTEXT for row-level security), access tokens
DbTransactionInterceptorTransactionsDiagnostics
SaveChangesInterceptorSaveChangesAudit fields, domain events, outbox
IMaterializationInterceptorEntity instance creationInjecting services, post-load initialization
IQueryExpressionInterceptorThe LINQ expression tree before compilationRewriting queries, enforcing rules
Interceptors are on the hot path Command interceptors run for every command. Keep them cheap. No I/O, no heavy allocation, no locks. Register stateless interceptors as singletons and add them once with AddInterceptors.

Example: audit fields with SaveChangesInterceptor

```csharp public interface IAuditable { DateTime CreatedUtc { get; set; } DateTime? ModifiedUtc { get; set; } } public sealed class AuditInterceptor(TimeProvider clock) : SaveChangesInterceptor { public override ValueTask> SavingChangesAsync( DbContextEventData eventData, InterceptionResult result, CancellationToken ct = default) { var now = clock.GetUtcNow().UtcDateTime; foreach (var e in eventData.Context!.ChangeTracker.Entries()) { if (e.State == EntityState.Added) e.Entity.CreatedUtc = now; if (e.State == EntityState.Modified) e.Entity.ModifiedUtc = now; } return ValueTask.FromResult(result); } } ```

Example: query hints by tag

Combine a query tag (Lesson 19) with a command interceptor to add a hint to specific queries only, for example to fight parameter sniffing:

```csharp public sealed class RecompileHintInterceptor : DbCommandInterceptor { public const string Tag = "-- hint:recompile"; public override ValueTask> ReaderExecutingAsync( DbCommand command, CommandEventData eventData, InterceptionResult result, CancellationToken ct = default) { if (command.CommandText.StartsWith(Tag, StringComparison.Ordinal)) command.CommandText += " OPTION (RECOMPILE)"; return ValueTask.FromResult(result); } } var rows = await db.Orders.TagWith("hint:recompile").Where(o => o.CustomerId == id).ToListAsync(); ```

Global query filters

A query filter is a predicate EF adds automatically to every query on an entity type, including Includes and navigations:

```csharp public class ShopContext(DbContextOptions options, ITenantProvider tenant) : DbContext(options) { private readonly int _tenantId = tenant.CurrentTenantId; protected override void OnModelCreating(ModelBuilder b) { b.Entity().HasQueryFilter(o => !o.IsDeleted && o.TenantId == _tenantId); } } // Bypass when needed (admin screens, data fixes): var all = await db.Orders.IgnoreQueryFilters().ToListAsync(); ```

The context field _tenantId is read per query and sent as a parameter, so the query cache still works. With pooling, use the factory pattern from Lesson 20 instead of constructor injection.

New in EF Core 10: named query filters Before EF 10, an entity type could have only one filter. Calling HasQueryFilter again replaced it, and IgnoreQueryFilters() was all or nothing. EF 10 lets you name filters and disable them selectively: ```csharp b.Entity() .HasQueryFilter("SoftDelete", o => !o.IsDeleted) .HasQueryFilter("Tenant", o => o.TenantId == _tenantId); // Show deleted orders, but still only for this tenant var bin = await db.Orders.IgnoreQueryFilters(["SoftDelete"]).Where(o => o.IsDeleted).ToListAsync(); ```

Indexing for filters

Every query on a filtered entity now includes the filter predicate, so your indexes must account for it:

  • Multi-tenancy: put TenantId first in your composite indexes: (TenantId, CustomerId, PlacedUtc).
  • Soft delete: use filtered indexes that only contain live rows: HasIndex(o => o.PlacedUtc).HasFilter("[IsDeleted] = 0"). They're smaller and match the predicate.
Filters and required navigations If Customer is soft-deleted and Order.Customer is a required navigation, an Include(o => o.Customer) uses an INNER JOIN, and the customer's filter makes those orders disappear from the results. Either filter both sides consistently or make the navigation optional. EF warns about this in the model validation logs.

Custom conventions

Conventions let you encode team rules once. For example, "every entity with a TenantId gets an index on it":

```csharp public sealed class TenantIndexConvention : IModelFinalizingConvention { public void ProcessModelFinalizing(IConventionModelBuilder modelBuilder, IConventionContext context) { foreach (var entityType in modelBuilder.Metadata.GetEntityTypes()) { if (entityType.BaseType is not null) continue; // root types only var tenant = entityType.FindProperty("TenantId"); if (tenant is not null) entityType.Builder.HasIndex(new[] { tenant }); } } } protected override void ConfigureConventions(ModelConfigurationBuilder configurationBuilder) { configurationBuilder.Conventions.Add(_ => new TenantIndexConvention()); } ```

You can also remove conventions you don't want. For example, configurationBuilder.Conventions.Remove(typeof(ForeignKeyIndexConvention)); stops automatic FK indexes when you manage all indexes yourself. Do this only deliberately.

Exercise

🛠 Production-grade cross-cutting concerns

  1. Add IsDeleted and TenantId to Order and Customer, with named filters (EF 10) or a combined filter (EF 8/9).
  2. Override delete behaviour: in a SaveChangesInterceptor, turn EntityState.Deleted into a modification that sets IsDeleted = true.
  3. Add a CommandCountingInterceptor that counts commands per request (store the counter in an AsyncLocal or a scoped service) and logs a warning above 10. Use it to catch an N+1.
  4. Create the matching tenant-first and filtered indexes and check the plans.
Soft-delete interceptor sketch ```csharp public override ValueTask> SavingChangesAsync(DbContextEventData e, InterceptionResult r, CancellationToken ct = default) { foreach (var entry in e.Context!.ChangeTracker.Entries().Where(x => x.State == EntityState.Deleted)) { entry.State = EntityState.Modified; entry.Entity.IsDeleted = true; } return ValueTask.FromResult(r); } ```
