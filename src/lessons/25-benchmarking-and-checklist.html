Benchmarking with BenchmarkDotNet

Stopwatch loops lie. They include JIT time, ignore GC, and suffer from noise. BenchmarkDotNet handles warm-up, statistics and memory measurement for you.

```csharp label="Benchmarks.cs" using BenchmarkDotNet.Attributes; using BenchmarkDotNet.Running; [MemoryDiagnoser] public class ReadBenchmarks { private PooledDbContextFactory _factory = null!; private static readonly Func> Compiled = EF.CompileAsyncQuery((ShopContext db, int cat) => db.Products.Where(p => p.CategoryId == cat) .Select(p => new ProductListItem(p.Id, p.Name, p.Price, p.Category.Name))); [GlobalSetup] public void Setup() { var options = new DbContextOptionsBuilder() .UseSqlServer("Server=localhost;Database=ShopBench;Trusted_Connection=True;TrustServerCertificate=True") .Options; _factory = new PooledDbContextFactory(options); // Seed once here (or beforehand) with realistic volumes. } [Benchmark(Baseline = true)] public async Task Tracking() { await using var db = _factory.CreateDbContext(); return (await db.Products.Where(p => p.CategoryId == 1).ToListAsync()).Count; } [Benchmark] public async Task NoTracking() { await using var db = _factory.CreateDbContext(); return (await db.Products.AsNoTracking().Where(p => p.CategoryId == 1).ToListAsync()).Count; } [Benchmark] public async Task Projection() { await using var db = _factory.CreateDbContext(); return (await db.Products.Where(p => p.CategoryId == 1) .Select(p => new ProductListItem(p.Id, p.Name, p.Price, p.Category.Name)).ToListAsync()).Count; } [Benchmark] public async Task CompiledProjection() { await using var db = _factory.CreateDbContext(); var n = 0; await foreach (var _ in Compiled(db, 1)) n++; return n; } } public static class Program { public static void Main(string[] args) => BenchmarkRunner.Run(); } ``` ```bash dotnet run -c Release ```
Benchmarking rules
  • Always run in Release, with no debugger attached.
  • Benchmark against the real provider (SQL Server or PostgreSQL in a container), never the InMemory provider. It has completely different performance characteristics.
  • Use realistic data volumes and distributions. 10 rows tell you nothing.
  • Look at Allocated as well as Mean. GC pressure hurts throughput under load.
  • Remember network latency. A local database hides round-trip costs that dominate in the cloud.

Load testing

Micro-benchmarks compare techniques. Load tests show how the whole system behaves under concurrency, including connection pool limits, locks and thread-pool starvation.

```javascript label="k6 script (load.js)" import http from 'k6/http'; import { check } from 'k6'; export const options = { vus: 50, duration: '60s' }; export default function () { const res = http.get('https://localhost:5001/api/products?categoryId=1'); check(res, { 'status 200': (r) => r.status === 200 }); } ```

Track p95/p99 latency and throughput, not averages, and watch the database side (CPU, waits, blocking) at the same time.

Guarding against regressions

Performance fixes erode as code changes. Lock the important ones in with integration tests, using Testcontainers for a real database:

```csharp public sealed class CommandCounter : DbCommandInterceptor { public int Count; public override InterceptionResult ReaderExecuting( DbCommand c, CommandEventData e, InterceptionResult r) { Interlocked.Increment(ref Count); return r; } public override ValueTask> ReaderExecutingAsync( DbCommand c, CommandEventData e, InterceptionResult r, CancellationToken ct = default) { Interlocked.Increment(ref Count); return ValueTask.FromResult(r); } // Add NonQueryExecuting/ScalarExecuting overrides to also count ExecuteUpdate/ExecuteDelete/ExecuteSql. } [Fact] public async Task Order_list_endpoint_runs_a_single_query() { var counter = new CommandCounter(); await using var db = CreateContext(o => o.AddInterceptors(counter)); var result = await new OrderQueries(db).GetRecentOrdersAsync(customerId: 1); Assert.NotEmpty(result); Assert.Equal(1, counter.Count); // catches an N+1 the day someone introduces it } [Fact] public void Product_list_query_does_not_select_description() { using var db = CreateContext(); var sql = new ProductQueries(db).ListQuery(categoryId: 1).ToQueryString(); Assert.DoesNotContain("[Description]", sql); } ```

The EF Core performance checklist

Configuration

  • ☐ DbContext is scoped (or created from a factory), never a singleton.
  • ☐ EnableSensitiveDataLogging and EnableDetailedErrors are off in production.
  • ☐ Retry-on-failure is enabled for cloud databases, and manual transactions run inside the execution strategy.
  • ☐ Performance warnings (multiple collection include, etc.) are configured to throw in development.
  • ☐ DbContext pooling is considered for high-throughput services, and the context has no stray state.
  • ☐ Database settings are bound to validated options with ValidateOnStart. Misconfiguration fails the deploy, not the first request.
  • ☐ No credentials in source control. Secrets come from a vault or environment, and managed identity is used where available.
  • ☐ Connection strings set Application Name and keep Encrypt on, and there's no TrustServerCertificate in production.
  • ☐ Provider settings match the server: compatibility level / PostgreSQL version, command timeout, UTC timestamps.
  • ☐ A database readiness health check exists, and liveness doesn't depend on the database.

Model

  • ☐ Strings have max lengths, non-Unicode where appropriate, and decimals have explicit precision.
  • ☐ Indexes exist for the WHERE, JOIN and ORDER BY patterns of the hot queries. Composite column order is correct.
  • ☐ Covering or filtered indexes are used where projections and filters allow.
  • ☐ The inheritance strategy fits the query patterns (TPH by default, TPC for leaf queries).
  • ☐ A compiled model is used for large models, generated automatically.

Queries

  • ☐ Every list endpoint is paged with a server-enforced maximum. Keyset paging is used for deep or infinite lists.
  • ☐ Read paths use projections or AsNoTracking.
  • ☐ There's no N+1. Lazy loading is off, or monitored.
  • ☐ Filtering and aggregation run in the database. There's no premature ToList() or IEnumerable.
  • ☐ Multiple collection loads use split queries or projections, measured.
  • ☐ Dynamic queries are parameterized, and the query cache hit rate is close to 100%.
  • ☐ Async APIs are used with CancellationToken in web code.

Writes

  • ☐ There's no SaveChanges inside loops. Changes are batched.
  • ☐ ExecuteUpdate/ExecuteDelete are used for set-based changes.
  • ☐ Bulk copy is used for large imports. Long-running imports clear the change tracker.
  • ☐ Optimistic concurrency protects contended entities.
  • ☐ Transactions are short, with no external I/O inside them.

Operations

  • ☐ Slow-query logging, query tags, and OpenTelemetry traces and metrics are in place.
  • ☐ Query Store or pg_stat_statements is enabled and reviewed regularly.
  • ☐ Migrations are deployed as scripts or bundles, not Migrate() at startup.
  • ☐ Warm-up runs before readiness. Benchmarks and query-count tests run in CI.

🔑 Key takeaways

  • Benchmark with BenchmarkDotNet, in Release, against the real provider, with realistic data.
  • Load test for p95/p99 latency and throughput while watching the database.
  • Lock in fixes with tests: command counts, generated-SQL assertions.
  • Use the checklist to audit configuration, model, queries, writes and operations.

🏆 Capstone project

Optimize "SlowShop"

Build, or take from your playground, an API with these deliberately slow endpoints, then apply the course:

  1. GET /products?page=N: loads all products with Include(Category), pages in memory, and returns entities including Description.
    Target: projection, keyset paging, covering index.
  2. GET /customers/{id}/dashboard: lazy loads orders and lines, and computes totals in C#.
    Target: one projected query with database-side aggregation.
  3. POST /orders/import: inserts 20,000 orders with SaveChanges per row.
    Target: batched saves with chunking, or bulk copy.
  4. POST /products/reprice: loads every product in a category, updates the price, and saves.
    Target: ExecuteUpdateAsync.
  5. GET /search?filters=…: builds dynamic expressions with Expression.Constant.
    Target: parameterized filters, verified with a cache hit-rate metric.

For each endpoint, record before and after: query count, rows read, p95 latency under load, and allocated memory. Write a short report of what you changed and why. That report is evidence you can now tune EF Core in production.
